# Decisions

Settled choices and their reasons. To reverse one, add a new entry that supersedes it. Never edit an old entry.

| # | Date | Decision | Why |
|---|---|---|---|
| 1 | 2026-09-22 | Build Tally as a new project instead of porting the Django app | The Django app was built for public signups and many users. Tally only needs to serve one family, plus a public demo, so it can be much simpler. |
| 2 | 2026-09-22 | Every part must be explainable in one plain sentence | The owner directs AI-written code and must be able to explain every part in their own words, including in interviews. |
| 3 | 2026-09-22 | Plaid for automatic bank sync | The owner chose auto-sync over statement uploads. Production Plaid access already exists. |
| 4 | 2026-09-22 | Fresh start; no data migration from Django | Simplest option. Plaid backfills history when a bank is linked. |
| 5 | 2026-09-22 | One shared household, no per-user permissions | The whole family shares one budget. Changes record who made them. |
| 6 | 2026-09-22 | Server-rendered HTML (Hono JSX) + HTMX, not React | It's the simplest option the owner can explain, and it matches the "server owns state" approach from the Django app. |
| 7 | 2026-09-22 | Ship the demo first, then Plaid for the family, then the remaining features in both environments | The portfolio demo goes live early. The family gets the core before the extras. |
| 8 | 2026-09-22 | GitHub Issues + one milestone per phase; `ROADMAP.md` links to them | Built-in progress tracking, and pull requests close issues. Nothing is written in two places. |
| 9 | 2026-09-22 | Jev for categories and flags | A fast, cheap classifier with confidence scores. The owner has early access and accepts the risk that comes with it. |
| 10 | 2026-09-22 | Workers AI for merchant name suggestions, which people accept or reject | Runs on the same Cloudflare account, with no extra vendor or key. Follows the rule "the app helps, it doesn't decide." |
| 11 | 2026-09-22 | No general LLM (Claude, DeepSeek) in the app for now | None of the 8 features needs one. The "ask a question" box is on the Later list. |
| 12 | 2026-09-22 | Cloudflare Workers + D1 + R2, with one Worker deployed as two environments | No servers to run. The demo and family app share code but never share data. |
| 13 | 2026-09-22 | Money stored as integer cents | SQLite has no exact decimal type, and integers avoid floating-point errors. |
| 14 | 2026-09-22 | Cloudflare Access for family login; no auth code in the app | Removes signup, passwords, and rate limiting from the codebase. |
| 15 | 2026-09-22 | Public repo | Portfolio visibility. Secrets live only in Wrangler secrets and a git-ignored `.dev.vars`. |
| 16 | 2026-09-22 | The Django app stays up until Tally replaces it; `finance.thesuperhuman.us` DNS is only changed with the owner's explicit approval | Beta users depend on it. |
| 17 | 2026-09-22 | Identify the user from Cloudflare Access's signed login token (`Cf-Access-Jwt-Assertion`), not the plain email header; Plaid webhooks use an Access Bypass policy for that one path | Cloudflare recommends validating the token. A misconfigured rule can't be used to fake who made a change. |
| 18 | 2026-09-22 | One Jev call per transaction, asking the category and all flags together | Jev's docs recommend bundling questions in one call, which is cheaper and faster than one call per question. |
| 19 | 2026-09-22 | Call Plaid and Jev over plain `fetch`, not their SDKs | Neither SDK is confirmed to work on Workers, and `fetch` is one less dependency to explain. |
| 20 | 2026-09-22 | Visual direction "Quiet ledger": shares thesuperhuman.us foundations (paper, ink, rule, Newsreader + Inter); green/brick-red status bars; terracotta only for navigation | Chosen from three generated studies. It ties Tally to the owner's site, and the status colors never double as brand color. See docs/design-concepts/README.md. |
| 21 | 2026-09-22 | Design process: generated studies (GPT images) before UI code, then a small design system built foundations → tokens → components → patterns, following the owner's personal-site process and designsystems.one | This replaces "wireframes before UI code." Studies set the direction; HTML and tokens are the real system. |
| 22 | 2026-09-22 | Frontend assets from our own origin: htmx 4 vendored from npm at build time, Inter + Newsreader self-hosted (OFL), icons copied from Lucide (ISC) into `src/views/icons.tsx` with no package dependency | The CSP can stay `'self'`, nothing loads from third-party CDNs, and each piece is one sentence to explain. Tailwind v4 is the CSS build tool named in spec §4. |
| 23 | 2026-09-22 | Data model clarifications: flags as three 0/1 columns; categories store icon + color token; accounts may lack a Plaid item; income is excluded from spending math | Each removes an ambiguity in spec §5–§6 with the simplest representation. See Phase 1b plan. |
| 24 | 2026-09-23 | CI screenshots every page with Playwright (dev dependency) and stores the images on an orphan `screenshots` branch, linked from the PR description | Owner request (#39). The spec already names Playwright for E2E. A branch in this public repo needs no extra service or secret, and the owner reviews UI without running the app. |
| 25 | 2026-09-23 | The nightly demo reset runs only when `DEMO` is `"true"` and no Plaid credentials are present | Owner request. The reset deletes every table. Production always has Plaid credentials and the demo never does (spec §4), so one mistaken variable can no longer wipe the family's data. |
| 26 | 2026-09-24 | The demo lives at `tally-demo.thesuperhuman.us` (was `demo.thesuperhuman.us`), served as a Workers Custom Domain with `workers.dev` and preview URLs off | Owner request. The name says which app it is, which suits a site that will show more than one project, and it leaves `demo.` free. One public address means one thing to check. |
| 27 | 2026-09-24 | A stored `category_confidence` with no category means "Jev looked and wasn't sure"; the nightly job asks Jev only about transactions with neither | Jev isn't re-asked (and re-billed) about the same transaction every night, only failed calls are retried, and it needs no new column. A person's choice clears the confidence, as it already does. |
| 28 | 2026-09-24 | Jev is still asked all three flags (decision 18), but its income answer isn't stored until the edit panel can change flags (#27); transfer and reimbursement are stored | An income flag takes a transaction out of spending and out of "needs a category", and today a person couldn't undo a wrong one (Greptile, #48). Transfer and reimbursement don't change any numbers until exclusions arrive with #27, which also adds the controls. |
| 29 | 2026-09-25 | Jev's category question offers "None of these fit", and Jev's pick is stored in a new `transactions.jev_category_id` column even below the threshold | Owner request after Jev's first demo run (#49): Household was acting as a catch-all (an unknown PayPal shop got it at 0.89), and picks below the threshold were lost, leaving nothing to tune the threshold from. The threshold stays 0.80. |
| 30 | 2026-09-25 | Suggesting a new category when Jev says none fit is in scope for Phase 4: Workers AI suggests a name through `src/ai/suggest-name.ts`, and a person creates or dismisses it in Settings | Owner approval. It closes the loop "None of these fit" opens (decision 29) without the AI ever creating categories itself. It isn't one of the eight numbered features; like merchant-name cleanup, it supports categorizing. |
| 31 | 2026-09-25 | A new `transactions.jev_failed_at` records when Jev last failed on that one transaction; the nightly job asks about never-failed transactions first and previously failed ones last, oldest failure first | Transactions that keep failing for their own reasons can't block the rest (Greptile P1 on #52): the three-in-a-row stop then only ever trips after the good ones are done. Nothing is given up on, so everything is retried once Jev recovers, and outages (no response, 401, 403, 429, 5xx) mark nothing. |
| 32 | 2026-09-25 | Every new database starts with 14 default categories (adapted from the owner's earlier app), and Settings for categories and budget amounts moves into Phase 2 (#55) | Owner request in the Phase 1 review (#53). Production starts empty, so without it the family couldn't budget in the trial week; starting everyone from the same list worked well in the earlier app. Income, transfers, payments, savings, refunds and "Other" are left out because flags, exclusions and "None of these fit" already cover them. |
| 33 | 2026-09-25 | Exclusions (#27: the toggle, and excluding what Jev flags `transfer` or `reimbursement`) move from Phase 3 to Phase 2 | Phase 1 review (#53). With real bank data, transfers and card payments would otherwise count as spending all through the trial week, with no way to fix them. Follows decision 28: a flag is applied once a person can undo it. |
| 34 | 2026-09-25 | The family app lives at `tally.thesuperhuman.us` | Owner choice at the start of Phase 2. It matches `tally-demo`, and leaves `finance.thesuperhuman.us` with the Django app until moving it is approved on its own (decision 16). |
| 35 | 2026-09-25 | Settings and Accounts are built from generated design studies the owner selects (round 5), not only from existing components | Owner choice at the start of Phase 2. Both are new screens, and the design system says visual changes start with a study. |
| 36 | 2026-09-25 | Local development uses Plaid Sandbox keys in the owner's `.dev.vars`; production keys exist only as production Worker secrets | Owner choice at the start of Phase 2. Sandbox gives realistic fake banks with no real data on a laptop; tests still fake Plaid at `fetch`. |
| 37 | 2026-09-25 | At most 50 categories are active at once (was 254, Jev's limit) | Owner decision while reviewing #63: the list should never need pagination. Settings, Home and the edit panel's chips each show every category at once, and paging Settings would break Move up and Move down, whose order is the order everywhere. Most households use 10–30; the defaults are 14. Archived categories don't count. |
| 38 | 2026-09-26 | Budgets are set on Home: a budget row (or a "Not budgeted" category) opens a sheet for its amount. Settings keeps names, order, archive and restore | Owner request after Settings (#55) shipped: changing a budget in Settings felt odd; the original app and Mint changed it where the bars are (#66). One place to set a budget, and it's where you see it. |
| 39 | 2026-09-26 | `public/js/money.js` joins the allowed custom JavaScript: the money input's cent and dollar nudges, round-up and last-month chips, and two-decimal cap | Owner choice (#66, audit #65): the original app's instant nudges were a detail worth keeping, and a server round trip per tap would feel slow. It's small, has no dependencies, keeps all math in integer cents, and without it the field still works. |
| 40 | 2026-09-26 | The money input's ▲▼ cent arrows are 44px wide but half the field's height (about 33px), an exception to the 44px touch-target rule | Owner's choice (#75): the input is the owner's own design from the original app, and they asked to keep its look and widen only the tap area. They still meet WCAG 2.5.8's 24px minimum. **Superseded by decision 41.** |
| 41 | 2026-09-26 | Supersedes 40: the money input's field is 90px tall, so each stacked cent arrow is a full 44×44 and there's no exception to the touch-target rule | Owner's pick after seeing both side by side (#75): the taller field keeps the original design's look, and the cent arrows now meet the 44px rule, so adjacent ▲▼ are harder to mis-tap. |
| 42 | 2026-09-26 | A design system catalog at `/design-system` renders every component by importing the real Hono JSX components with typed fake data. It is mounted only when `DEMO` is `"true"` (the demo and development) and returns 404 in production | Owner request (#76) after the money input drifted from the owner's design (#75). The original app's catalog kept components in one place; importing the real component means the catalog can't show a copy that has drifted. Showing it on the demo makes the design system part of the portfolio, and production never needs it. |
| 43 | 2026-09-26 | Every UI change starts in the catalog: build or change the component there at its tier (Visual, Interactive, Flow), audit it against `DESIGN.md`, screenshot it at 1280 and 390, and the owner signs it off there before it reaches an app page. New screens still start with a generated study (decisions 21 and 35); components start directly in the catalog | Owner choice (#76), adapted from the original app's design-system integrity protocol. Owner-designed details were being lost or reinvented because there was no place to see and approve a component on its own. |
| 44 | 2026-09-26 | `public/js/ds.js` joins the allowed custom JavaScript, served only on catalog pages: it runs the catalog's own controls (for example firing a sample toast or replaying an animation). It never intercepts or fakes server requests, and app pages never load it | Owner choice (#76). Some Interactive-tier demos need a button to trigger them. The original app's request-intercepting sandbox created bugs of its own, so the script is limited to catalog controls; anything that needs the server is Visual in the catalog and works in a Flow. |
| 45 | 2026-09-26 | Swipe gestures, drag and modal dialogs from the original app are kept as enhancements: the app works without each one, each one's script is its own allowed-JS decision when it's built, and each is designed in the catalog first. What each gesture does in Tally is agreed with the owner before it's built | Owner request (#76): none of them is needed, but they make the app feel better, and the original had them. Keeping the no-script path means a failed or blocked script never breaks a page. |
| 46 | 2026-09-26 | The owner's answers to the design-language audit (#79, `docs/design-system/audit-2026-09-26.md`): (1) the safe-to-spend number is on a phone's first screen: the demo's Things to try moves below the Budget list and the month title becomes smaller than the number; (2) until a person names a merchant, its raw bank text is tidied by code for display (prefixes removed, sentence case), with `raw_name` unchanged; (3) the money input keeps its round ±$1 buttons either side of the field, from the original's hero-amount dialog, not the catalog's stacked box; (4) budget bars become thinner and lighter so the words lead, designed in the catalog first | The brief: Tally should feel like a breath of fresh air to people who gave up on budgeting apps. Each answer removes something the audit found fighting that feeling: the one number pushed down the screen, a list that reads like a bank statement, and bars louder than the words. Tidying names is code, not AI, so "AI suggests" still applies to Phase 4's name suggestions (#33), which replace it. |
