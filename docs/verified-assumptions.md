# Verified assumptions (spec §13)

Checked on: 2026-09-22

| # | Assumption | Result | Source | Spec change needed? |
|---|---|---|---|---|
| 1 | Workers + static assets is Cloudflare's recommended path for new full-stack apps (vs Pages) | Confirmed, informally. Cloudflare has not published a single "always use Workers" statement, but every current signal points there: Workers static assets reached feature parity with Pages (SSR, custom domains) and gained a strictly larger feature set (Durable Objects, Cron Triggers, richer Observability) that Pages does not get; Pages is in maintenance mode (bug fixes only) while Workers gets the new roadmap. Cloudflare's own migration guide is one-directional (Pages → Workers, not the reverse). | https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/ | No |
| 2 | Hono on Workers: routing, JSX, scheduled + webhook handlers | Confirmed (2026-09-22, prior check) and reconfirmed. `export default { fetch: app.fetch, scheduled: async (batch, env) => {} }` is Hono's documented pattern for adding a `scheduled` handler in Module Worker mode — `app.fetch` is exported as the Worker's `fetch`, and any other event handler (e.g. `scheduled`) is added as a sibling property on the same default export object. `new Hono<{ Bindings }>()` and JSX via `jsx: "react-jsx"` + `jsxImportSource: "hono/jsx"` also confirmed. A webhook route is just a normal Hono route (`app.post("/webhooks/plaid", ...)`); nothing Hono-specific is needed beyond reading the raw body for signature verification. | https://hono.dev/docs/getting-started/cloudflare-workers | No |
| 3 | D1: `batch()` is atomic (for the sync save); migrations workflow; Time Travel retention window | Confirmed. `D1Database.batch()` sends an array of prepared statements as one call; D1 documents batched statements as SQL transactions — "if a statement in the sequence fails, then an error is returned for that specific statement, and it aborts or rolls back the entire sequence." This is exactly the semantics the spec needs for saving synced transactions + cursor together. Migrations: numbered files in `migrations/`, applied with `wrangler d1 migrations apply <DATABASE> [--local\|--remote]`; a backup is captured after a successful apply, and a failed migration is rolled back leaving the previous one applied. Time Travel: restores to any minute within the retention window via `wrangler d1 time-travel restore <DB> --timestamp=... ` (or `--bookmark=...`); retention is **30 days on Workers Paid, 7 days on Workers Free**, at no extra storage/restore cost. | https://developers.cloudflare.com/d1/worker-api/d1-database ; https://developers.cloudflare.com/d1/reference/migrations ; https://developers.cloudflare.com/d1/reference/time-travel | No |
| 4 | Vitest + Cloudflare Workers test integration with local D1 | Confirmed (2026-09-22, prior check): package is `@cloudflare/vitest-plugin`, configured via `cloudflareTest({ wrangler: { configPath } })`; `exports.default.fetch()` is imported from `cloudflare:workers` in tests; it does not serve static assets. Added detail: local D1 in tests is wired up with two helpers from the plugin, `readD1Migrations` (reads the `migrations/` directory into a test-only binding, conventionally `TEST_MIGRATIONS`) and `applyD1Migrations` (applies them to the test D1 binding), invoked from a Vitest `setupFiles` script (e.g. `test/apply-migrations.ts`) that runs before each test file. The Worker under test then uses the same `env.DB` binding it uses in production, but all reads/writes land in the local, migrated, isolated D1 instance. | https://developers.cloudflare.com/workers/testing/vitest-integration/configuration/ ; https://developers.cloudflare.com/workers/testing/vitest-integration/recipes/ (D1 recipe, referenced) | No — spec §11 ("Vitest with Cloudflare's Workers test integration") already covers this |
| 5 | Plaid: fetch vs Node SDK on Workers; `/transactions/sync` pagination; webhook signature verification; Link update mode | Partially confirmed, with a recommendation change. The official `plaid` Node SDK is axios-based; axios itself does not run natively on Workers (community consensus: needs a fetch-shim like `redaxios`, which itself lacks retries/interceptors/auth helpers the real SDK provides), and even with `nodejs_compat` there's no first-party confirmation from Plaid or Cloudflare that the SDK is supported on Workers. **Recommendation: call the Plaid REST API directly with `fetch`**, as the spec already states — this avoids an unsupported dependency entirely. `/transactions/sync`: response has `added`, `modified`, `removed`, `next_cursor`, `has_more`; call with no cursor the first time, save `next_cursor`, and if `has_more` is `true` repeat with `cursor` set to the last `next_cursor` until `has_more` is `false`; the final cursor is valid for at least 1 year. Webhook verification: signature arrives as a JWT in the `Plaid-Verification` header; verify `alg` is `ES256` (reject otherwise), extract `kid`, fetch the matching JWK from `/webhook_verification_key/get`, and verify the JWT with that key — Plaid explicitly recommends using a well-tested JWT/JWK library rather than a hand-rolled implementation (Web Crypto's `SubtleCrypto.verify` with `ECDSA`/`P-256` works in Workers). Link update mode: create a new `link_token` with the existing Plaid `access_token`'s Item (`user.client_user_id` + item context) to re-open Link in update mode when `ITEM_LOGIN_REQUIRED` (or `PENDING_EXPIRATION`/`PENDING_DISCONNECT`) fires; a link_token for update mode expires after 30 minutes (vs. 4 hours for a normal link_token). | https://plaid.com/docs/api/products/transactions/ ; https://plaid.com/docs/api/webhooks/webhook-verification/ ; https://plaid.com/docs/link/update-mode/ ; https://developers.cloudflare.com/workers/runtime-apis/nodejs/http/ | Yes |
| 6 | Cloudflare Access: bypassing a single path (`/webhooks/plaid`) and reading the authenticated-email header | Confirmed, with a security recommendation change. Bypassing one path: Access supports a **Bypass** policy (`"decision": "bypass"` in the API), which can be scoped to a specific application path — Cloudflare's own docs give exactly this pattern for "endpoints that must be publicly reachable, such as OAuth callback URLs, webhook receivers, or health check paths," e.g. a separate Access application scoped to `yourapp.com/webhooks/plaid` with a Bypass policy; Bypass policies are evaluated before Allow/Block. Header: Cloudflare does send `Cf-Access-Authenticated-User-Email` to the origin, but **Cloudflare's own guidance is to validate the `Cf-Access-Jwt-Assertion` JWT at the origin, not just trust the email header** — "Cloudflare recommends validating the Cf-Access-Jwt-Assertion header instead of the CF_Authorization cookie" and explicitly: "you must validate the application token issued by Cloudflare Access... to ensure that any requests which bypass Cloudflare Access (for example, due to a network misconfiguration) are rejected." The JWT is signed with a per-account key pair; the public key/JWKS lives at `https://<team-name>.cloudflareaccess.com/cdn-cgi/access/certs`. (Separately, Workers now also expose a `ctx.access` API that reads the verified identity — email, groups, device posture — without manual JWT parsing, per Cloudflare's Workers docs; this could replace hand-rolled verification but needs its own check before adoption since detail was thin.) Free plan: Cloudflare Access on the Free plan supports **up to 50 users** at no cost; paid seats are needed beyond that. | https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/validating-json/ ; https://developers.cloudflare.com/cloudflare-one/access-controls/policies/ (Bypass policy) ; https://developers.cloudflare.com/workers/configuration/cloudflare-access/ ; https://www.cloudflare.com/plans/zero-trust-services/ | Yes |
| 7 | Jev: request/response format, confidence, 255-choice limit, error handling | Confirmed via https://docs.typesafe.ai/api and linked sub-pages. Single endpoint `POST https://api.typesafe.ai/v1/systemone`, auth via `Authorization: Bearer <API_KEY>` + `Content-Type: application/json`. Request body: `state` (string or structured object/array — the content to evaluate), `model` (use `"jev-latest"`), `questions` (a map of typed Question objects, keyed by names you choose). Question types ("primitives"): **Noul** (yes/no, returns a 0–1 probability), **Choice** (`type: "choice"`, `instructions`, `criteria` — a map of option-name → description; picks one option, returns the chosen option plus the full probability distribution; documented limit is **up to 255 options**), **Score** (rates on an ordered 2–10 level rubric, probability-weighted). Response: `model`, `answers` (map matching your question keys; Choice/Score answers include a `confidence` field between 0 and 1 "derived from the answer's probability distribution"), `usage.input_tokens`/`usage.output_tokens`. Multi-label/flags: **one call can return a category AND flags** — the docs' own "fan-out" pattern explicitly recommends bundling multiple questions (e.g. a Choice for category plus one or more Noul flags) into a single `questions` map in one request rather than issuing separate calls, and a cookbook states "batching every question into one TypeSafe call is 12.2x cheaper and 10.0x faster" than separate calls — this changes the spec's "Jev... category and flags" language to make explicit that both should be one bundled call, not two. Errors: HTTP status codes `401` (auth), `422` (validation), `429` (rate limit), `529` (overload); guidance is to retry with exponential backoff on `429`/`529`. SDKs: official `@typesafe-ai/sdk` npm package (TypeScript/JavaScript, requires Node.js 20+, exports a `TypeSafeClient` with a `systemOne()` method) and a Python SDK; **the JS SDK's Node.js 20+ requirement is not documented as Workers-compatible**, so plan to call the HTTP API directly with `fetch` from `src/ai/categorize.ts` rather than depend on the SDK, consistent with how the spec already isolates the Jev call behind one module. Exact numeric rate limits (requests/sec or /min) were **UNVERIFIED** — the docs describe a `RateLimitError`/`retryAfterMs` mechanism but no published numeric ceiling was found in the pages reached. | https://docs.typesafe.ai/api ; https://docs.typesafe.ai/primitives/choice ; https://docs.typesafe.ai/patterns/fan-out ; https://docs.typesafe.ai/sdk/javascript ; https://docs.typesafe.ai/sdk/javascript/api/classes/RateLimitError | Yes |
| 8 | Workers AI: model for merchant-name suggestions, pricing | Confirmed. Called via the `AI` binding: `await env.AI.run(model, inputs)`, e.g. `env.AI.run('@cf/meta/llama-3.1-8b-instruct', { prompt })`. For a small, cheap text-cleanup task like turning `"SQ *BLUE BTL COFFEE 4432"` into `"Blue Bottle Coffee"`, a small instruct model such as `@cf/meta/llama-3.1-8b-instruct` (or a smaller Llama/Gemma variant in the catalog) is an appropriate, low-cost fit — exact model choice should be validated against the current model catalog (`developers.cloudflare.com/workers-ai/models/`) at implementation time since the catalog changes. Pricing: Workers AI bills in **Neurons** — **10,000 neurons/day free**, then **$0.011 per 1,000 neurons** on the paid plan; there is no separate "Workers AI plan," it's billed per-account. | https://developers.cloudflare.com/workers-ai/configuration/bindings/ ; https://www.cloudflare.com/plans/ (Workers AI pricing table) ; https://developers.cloudflare.com/workers-ai/platform/pricing/ | No |
| 9 | R2: upload/download from a Worker; size limits | Confirmed. Binding usage: `env.MY_BUCKET.get(key)` to read (returns `null` if missing; body is a stream, `object.body`), `env.MY_BUCKET.put(key, value)` to write, `env.MY_BUCKET.delete(key)` to remove. Streaming an upload from a multipart form in a Worker: read the `request.body` stream directly (or `await request.formData()` and pull the `File`'s stream) and pass it to `put()`/multipart-upload `uploadPart()` — Cloudflare's example Worker implements a full multipart lifecycle (`mpu-create` → `uploadPart` per chunk → `mpu-complete`/`mpu-abort`) fronted by the Worker, specifically so uploads can **exceed the Workers request body size limit**, since each individual part is still subject to that limit but the assembled object is not. Object size limits: R2 objects can be very large (multi-TB via multipart); the binding path itself isn't the constraint — the **Workers request body size limit** is. Worker request body size limit is **tied to the zone's Cloudflare plan, not the Workers plan**: Free/Pro zones cap lower, and a **Business plan zone allows up to 200 MB** per request (Enterprise can raise it further); exceeding the limit returns `413 Request Entity Too Large`. For anything larger than the plan's per-request cap, the multipart-from-the-client pattern above (client uploads parts directly, or via the Worker acting as a relay per part) is required. | https://developers.cloudflare.com/r2/api/workers/workers-multipart-usage/ ; https://developers.cloudflare.com/workers/platform/limits/ | No — but implementation should note the plan-dependent body-size cap explicitly in code comments/docs |

## Notes per item

**1. Workers vs Pages.** No single "we recommend Workers over Pages" sentence exists in Cloudflare's docs, but the trajectory is unambiguous: Workers static assets now match Pages for SSR/custom domains and additionally get Durable Objects, Cron Triggers, and fuller Observability that Pages lacks, and Cloudflare only documents a Pages→Workers migration path, never the reverse. The spec's choice of Workers + static assets stands as-is.

**2. Hono.** No change from the prior confirmation. `export default { fetch: app.fetch, scheduled: async (batch, env) => {} }` is the exact documented shape; a webhook route (`/webhooks/plaid`) is an ordinary Hono `app.post(...)` handler with no special framework support needed — the work is all in reading the raw body/headers for Plaid's signature check.

**3. D1.** `batch()`'s "aborts or rolls back the entire sequence" language is exactly the atomicity guarantee the sync-save design (§10) depends on: transactions + cursor update must all-or-nothing succeed. Migrations use `wrangler d1 migrations apply <DB> [--local|--remote]` against numbered files in `migrations/`, matching the spec. Time Travel retention is 30 days on Workers Paid (7 days Free) — this number should be written into the README as planned.

**4. Vitest.** Already confirmed package rename to `@cloudflare/vitest-plugin`; the added detail is that local D1 in route tests needs `readD1Migrations`/`applyD1Migrations` wired into a `setupFiles` script so `env.DB` in tests points at a freshly migrated local database before each test file runs.

**5. Plaid.** The spec already says "REST over fetch," which this check validates as the right call — the official SDK's axios dependency has no confirmed Workers support, so avoiding it avoids risk. `/transactions/sync`'s `added`/`modified`/`removed`/`next_cursor`/`has_more` fields and pagination loop match the spec's sync-loop design exactly. Webhook verification needs a JWT/JWK (ES256) check against `/webhook_verification_key/get`, which is more than a simple HMAC compare — this is a spec-detail gap worth calling out (see Proposed spec changes). Link update mode needs a freshly-created `link_token` scoped to the existing Item, and that token is short-lived (30 minutes), which affects the "Fix connection" UX (the link must be created just-in-time, not pre-generated).

**6. Cloudflare Access.** Two things changed from the spec's assumption: (a) bypassing `/webhooks/plaid` should use Access's dedicated **Bypass** policy type scoped to that path (via a second Access application or an app-path rule), not just "excluding" the route informally; (b) the spec should not rely on `Cf-Access-Authenticated-User-Email` alone for anything security-sensitive — Cloudflare's own docs say to validate the `Cf-Access-Jwt-Assertion` JWT at the origin so a network misconfiguration that skips Access can't spoof the email header. The free-plan 50-user cap is fine for a household app but worth recording.

**7. Jev.** This is the highest-value finding: Jev's own "fan-out" pattern documents that category + flags should go in **one** call as multiple keys in the `questions` map (e.g. `{"category": {type:"choice",...}, "is_transfer": {type:"noul",...}}`), which is cheaper and faster than two calls per the docs' own cookbook. The spec currently doesn't say explicitly whether category and flags are one call or two — this should be made explicit. The 255-option Choice limit matches the design (household category lists are nowhere near that). No confirmed numeric rate limit was found; treat this as an operational unknown to monitor once live, not a blocker.

**8. Workers AI.** `env.AI.run(model, inputs)` is confirmed and trivial to call from `src/ai/suggest-name.ts`. Exact model name should be picked from the live catalog at build time rather than hardcoded now, since Cloudflare updates the catalog frequently, but a small instruct model in the Llama 3.1 8B class (or smaller) is the right size class for a short merchant-name cleanup prompt. Pricing (10,000 free neurons/day, $0.011/1,000 neurons after) is cheap enough that this feature's usage pattern (once per unique `raw_name`, cached) is effectively free at household scale.

**9. R2.** Binding `get`/`put`/`delete` match the spec's simple document-storage need. The real limit to design around is the **Worker request body size limit**, which is plan-dependent (e.g. up to 200 MB on Business), not an R2-specific limit — for PDF uploads within that cap, a direct `put()` from the Worker is fine; nothing in the spec's Documents feature (§3 feature 8) suggests files anywhere near that size, so no multipart-upload complexity is needed at launch.

## Proposed spec changes

**Item 5 — Plaid webhook verification detail.**
- Current spec text (§10): "Plaid webhook | Verify Plaid's webhook signature before acting."
- Proposed replacement: "Plaid webhook | Verify the `Plaid-Verification` header: it is a JWT signed with `ES256`. Reject if `alg` is not `ES256`. Extract `kid`, fetch the matching key from `/webhook_verification_key/get` (cache it), and verify the JWT with that key using Web Crypto (`SubtleCrypto.verify`, ECDSA P-256) before acting on the payload."
- Also propose adding to §13 assumption 5 wording: note that the official Plaid Node SDK is not used (fetch-only), and that Link update mode's `link_token` must be created just-in-time (expires in 30 minutes) rather than reused.

**Item 6 — Cloudflare Access bypass + header trust.**
- Current spec text (§10): "Plaid webhook | ... The webhook route is the only path excluded from Cloudflare Access." and (§5) "`updated_by`, `linked_by`, and `uploaded_by` hold the email that Cloudflare Access passes in the `Cf-Access-Authenticated-User-Email` header."
- Proposed replacement: "The webhook route is excluded from Cloudflare Access via a Bypass policy scoped to that path (a second Access application for `.../webhooks/plaid`, or an app-path rule with `decision: bypass`), not a blanket route exclusion." And: "For anything used to attribute a write (`updated_by`, `linked_by`, `uploaded_by`), validate the signed `Cf-Access-Jwt-Assertion` JWT at the Worker (against the team's JWKS at `https://<team-name>.cloudflareaccess.com/cdn-cgi/access/certs`) and read the email claim from the verified token, rather than trusting the `Cf-Access-Authenticated-User-Email` header value directly, so a misconfigured Access rule can't let a bypassed request forge an identity."

**Item 7 — Jev category + flags in one call.**
- Current spec text (§7): "Jev. Send the transaction to Jev with the household's category list as the allowed outputs, along with the allowed flags. If the confidence is at or above the threshold, apply the category (`category_source = jev`). Otherwise leave the category null for review. Flags are applied the same way."
- Proposed replacement: "Jev. Send **one** `POST /v1/systemone` call per transaction with a `questions` map containing a `category` Choice question (options = the household's category list) and one `Noul` question per allowed flag, following Jev's documented fan-out pattern (bundling questions in one call, not one call per question, since that is Jev's own recommended and cheaper/faster usage). If the category answer's `confidence` is at or above the threshold, apply the category (`category_source = jev`); otherwise leave the category null for review. Apply each flag independently based on its own Noul probability/threshold."

Sources for all items above are cited inline in the table and notes; Context7 (Cloudflare D1, Cloudflare Workers, Hono) and official docs (developers.cloudflare.com, plaid.com/docs, hono.dev, docs.typesafe.ai) were used throughout, as directed. No claim in this file was guessed — anything not confirmed is marked UNVERIFIED (see item 7, exact numeric Jev rate limits).
