## Goal

Every Jev and Workers AI call runs as one queue message, each batch in its own Worker invocation, so a big backfill or a slow Jev never stops at one run's limits. D1 stays the record of what's waiting. The 09:00 run sweeps whatever is still waiting back onto the queue.

## What the Cloudflare docs say (checked 2026-10-18)

- Consumer settings: `max_batch_size` defaults to 10 (at most 100), `max_batch_timeout` to 5 s (at most 60), and `max_retries` to 3 (at most 100). `max_concurrency` scales up to 250 when it isn't set.
- `msg.attempts` starts at 1. `msg.retry({ delaySeconds })` accepts up to 86,400 (24 h). `msg.ack()` marks one message as done. The first call on a message wins, and a message's own call beats `ackAll` and `retryAll`.
- When the handler returns, every message it didn't retry is acknowledged. A throw, or a rejected `waitUntil` promise, retries the **whole batch**.
- Once its retries are used up, a message is deleted, or moved to the dead-letter queue when one is set. A dead-letter queue with no consumer keeps messages for 4 days.
- `sendBatch` takes at most 100 messages and 256 KB a call. A message is at most 128 KB. Order within a batch is best effort only.
- A consumer invocation gets 15 minutes of wall time and 30 s of CPU by default. D1 allows 1,000 queries per Worker invocation on Paid.
- Paid retention defaults to 4 days. Each message is about 3 operations, and each retry adds one read.
- Bindings (wrangler.jsonc): `"queues": { "producers": [{ "queue": "<name>", "binding": "<NAME>" }], "consumers": [{ "queue": "<name>", "max_batch_size": …, "max_retries": … }] }`. Env blocks don't inherit it, so each env lists its own.

## Choices made here (internals, not the owner's)

- **One queue per env:** `tally-jobs` (production) and `tally-demo-jobs` (demo). The binding is `JOBS` in both. The demo never shares a production binding (CLAUDE.md). The owner creates both queues (`npx wrangler queues create …`) before the first deploy, and the PR says so. The top-level config gets its own `tally-local-jobs` producer and consumer with the same `JOBS` binding, since `npm run dev` and `vitest.config.ts` (`configPath: "./wrangler.jsonc"`, no env) read the top level; Miniflare runs that queue locally.
- **Consumer config:** `max_batch_size: 10`, `max_batch_timeout: 5`, `max_retries: 3`, `max_concurrency: 1`, no `dead_letter_queue`. `max_concurrency: 1` only stops two consumer invocations running at once; it does nothing inside a batch. So the router also handles a batch's messages one after another (`for … of` with `await`, never `Promise.all`), and together they mean one Jev or Workers AI call at a time, under their rate limits. A batch of 10 sorts is about 40 D1 queries, far under 1,000.
- **Message body:** `{ type: "sort" | "name" | "note" | "suggest", id: number | string }`. `id` is the transaction id, or the raw bank text for `name`. `suggest` carries no id and regroups from D1 every time.
- **Retry delays:** `[60, 300, 1800]` seconds by `msg.attempts` (1, 2, 3). On attempt 4 (after the third retry) the job acknowledges instead of retrying, so Cloudflare never deletes a message on its own.
- **First night's counts (#586):** `keepNightCounts` moves from the 09:40 run to the 10:00 run, before the reminders. Today it declines only while a transaction waits for Jev or a bank text waits for its name (src/first-tally/night.ts:54-69), so a `suggest` still retrying at 10:00 would let a night count as clean too early. So the 10:00 run first runs the suggest pass itself (`suggestNewCategories`, the same body the `suggest` job uses). If that pass reports a temporary Workers AI failure, `keepNightCounts` keeps nothing that night, the same way a waiting name stops it. Once the pass finishes, nothing is left to suggest, and the counts include its suggestions.
- **The re-asks stay as they are:** `askAgain` after an untick or a note (src/routes/transactions.tsx:3170) and the settings, suggestions and organize re-asks keep running in `waitUntil`. They ask about one transaction each, so they never hit a limit. Moving them onto the queue is a follow-up, not this issue.
