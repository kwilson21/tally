# Tally — Design Spec

- **Date:** 2026-09-22
- **Status:** Approved by the owner (2026-09-25, Phase 1 review)
- **Owner:** Kazon Wilson

## 1. What Tally is

Tally is a family budgeting app. It pulls in bank transactions automatically, sorts them into categories with a small AI model, and shows the household how much is left to spend this month.

It serves two audiences from one codebase:

1. **The owner's household**: a private app behind a login wall, with real bank data.
2. **The public**: a portfolio demo at `tally-demo.thesuperhuman.us` with fake data only.

Tally replaces the owner's Django app (`personal-finance-app`). That app stays in place until Tally has fully taken over its job.

## 2. Guiding rules

1. **Explainable in one sentence.** Every part of the system must be explainable in one plain sentence, and this spec gives that sentence for each part. If the owner can't explain a part in their own words, it doesn't go in.
2. **The spec is the source of truth.** Nothing gets built unless it's in this spec. New ideas go on the Later list (§12) until the spec is updated.
3. **Decisions stay decided.** Settled choices are recorded in `docs/decisions.md` with their reasons. Reopening one takes a new decision entry, not a silent change.
4. **Simplicity beats keywords.** Tools are picked because they're the simplest fit, not because they appear on job postings.
5. **The server owns all state.** No client-side state framework.
6. **AI suggests; code calculates; people decide.** AI models classify and suggest. Deterministic code does all money math. People can override any AI output.

## 3. Scope

The first seven features ship across phases (§11); the eighth moved to the Later list (decision 66):

| # | Feature |
|---|---|
| 1 | Budget vs. spent this month, with category left and safe to spend |
| 2 | Bills: upcoming, overdue, paid |
| 3 | Transaction list: browse, search, recategorize |
| 4 | Splitting a transaction across categories |
| 5 | Excluding transactions from the budget (transfers, reimbursements, one-offs) |
| 6 | Spending trends: month over month, by category |
| 7 | Account balances and net worth over time |
| 8 | ~~Documents: stored statements and receipts (PDF)~~ Moved to the Later list as part of receipts (§12, decision 66) |

Also in scope: AI-suggested merchant name cleanup (accept or reject), AI-suggested new categories when none of the household's categories fit (a person creates or dismisses them), the demo banner with its Start here link, the three things to try (in How Tally works' Start here, decision 111), a "How it works" page, and onboarding: what a first visit shows and teaches, in the demo and in the family's first week (decision 49, #95).

**Household model:** one shared household. Everyone who can log in sees and edits the same data. Changes record who made them.

**Data:** fresh start. Nothing is migrated from the Django app. Banks are linked again, and Plaid backfills the history.

## 4. Architecture

> One small TypeScript server on Cloudflare builds each page, stores data in a SQLite database, pulls bank data from Plaid, and uses two AI models: Jev for categories and Workers AI for merchant names.

| Part | Job, in one sentence |
|---|---|
| **Cloudflare Worker (Hono, TypeScript)** | Handles every request: builds pages, receives Plaid webhooks, and runs scheduled jobs. |
| **HTMX** | When you click something, HTMX asks the server for a piece of new HTML and swaps it into the page. |
| **Tailwind CSS** | Styles the pages with utility classes, compiled into one CSS file. |
| **Workers static assets** | Serves the CSS file, `htmx.js`, and icons. |
| **D1 (SQLite)** | Stores all data. |
| **Plaid (REST over `fetch`)** | Supplies accounts, transactions, and balances from the family's banks. |
| **Jev (TypeSafe AI)** | Picks a category and flags for each transaction, with a confidence score. |
| **Workers AI** | Suggests a clean merchant name, which a person accepts or rejects. |
| **Resend** | Sends bank sign-in reminder emails; Cloudflare Email Service is the best-effort fallback for destinations verified in Cloudflare Email Routing (decision 86). |
| **Cron Triggers** | Run the daily bank sync (a backup for webhooks), one bank at a time so one failure doesn't stop the others, skipping any bank that needs reconnecting; then retry uncategorized transactions. A separate 10:00 UTC run sends due reconnect reminders. The demo has no bank sync or email: each night it resets to the seed data, then retries uncategorized transactions. |
| **Cloudflare Access** | A login wall with the family's emails in front of the family app; the app has no login code of its own. |
| **Wrangler** | The command-line tool that deploys the Worker and stores secrets. |

The account is on Workers Paid (decision 90), which the nightly design relies on: 1,000 D1 queries per invocation (50 on Free), long scheduled runs, and room for more Cron Triggers than Free's 5.

**How real data stays out of the demo:** the demo database is only ever built from seed files in the repo. The demo environment has no Plaid credentials and no binding to the production database or bucket, so no code path can reach real data.

## 6. Money rules and budget math

**Sign convention (Plaid's):** a positive amount is money out, and a negative amount is money in. Account balances on debt accounts (`is_liability`) display as negative.

**Dates:** transaction dates are stored and compared exactly as Plaid sends them (`YYYY-MM-DD`), with no time-zone conversion. A month is the `YYYY-MM` prefix of the date. "Today", which decides the current month and bill status, is the household's date in its time zone, a Settings choice that starts as Eastern (`America/New_York`); a transaction's own date is never converted (decision 67).

**Pending (decision 67):** a pending transaction counts like any other and shows the word "Pending". When the bank posts it under a new id, the person's category, note, exclusion and every link (bill, refund, counts in) move to the posted transaction, and so do Tally's own answer (§7, decision 79) and a split if the amount is unchanged; if the posted amount differs, the split is removed as in §6.1 (decision 62). A pending one the bank drops is removed with its links.

"Counted transactions" for a month means: date in that month (or, from Phase 3, a payment linked to an earlier month's bill occurrence counts in that occurrence's month instead, never both; decision 58, #26; and a refund linked to its purchase counts in the purchase's counted month and current category instead of its own, never both, while the purchase counts; if the purchase is excluded, even one that counts only because it pays a bill, the refund counts on its own date and category again; a refund of a split purchase links to one of its parts, decision 60), `excluded = false` (or a payment linked to a bill or a planned expense, which counts whatever its exclusion, §6.1 rule 4 and §8.4), and `is_split = false`, so split parents are skipped and their children count instead. An unreviewed negative bank credit (`COALESCE(credit_reviewed, 0) = 0`, not flagged as income) is held out of Spent, Uncategorized, and Safe to spend until Jev confidently categorizes it as non-income or a person marks it reviewed as a refund or other non-income credit (decision 70). Transactions flagged `income` are counted only toward **Income** and are left out of Spent, Uncategorized, and Safe to spend. A refund that follows its purchase has no category of its own to set, so only the purchase shows Needs category; its amount stays in Uncategorized until the purchase has a category.

### 6.1 Matching bills to payments

> The matcher gives each bill occurrence at most one payment, and each transaction pays at most one bill. (From Phase 5, decision 74: a person can link several payments to one occurrence, a bill paid in parts; the matcher still links one, and each transaction still pays at most one bill or one planned expense, never both.)

**The key:** a bill *occurrence* is identified by `(bill_id, period)`, where `period` is `YYYY-MM` for monthly bills and `YYYY` for yearly bills; from Phase 5 (decision 74), a weekly or every-two-weeks occurrence's own due date (`YYYY-MM-DD`) and a quarterly one's `YYYY-Qn`, the calendar quarter that holds its due date (Q1 is January to March; decision 79), so each key names exactly one occurrence. Unique constraints in `bill_payments` let the database itself rule out double matches in either direction, so re-running the matcher changes nothing. (From Phase 5 the one on (`bill_id`, `period`) is dropped for parts paid by hand, and the matcher instead skips any occurrence that already has a linked payment.)

**A transaction is a candidate for a bill occurrence only if all of these hold:**
1. **Merchant:** its merchant key equals the bill's. A transaction's merchant key is Plaid's `merchant_name` when present, otherwise its `raw_name`; a bill's is the key of the payment it was made from or linked to (from Phase 3.5, decision 67; before that, `raw_name` against `merchant_raw_name`). A bank text typed for a bill is saved as the key of the newest transaction whose raw name it is, when one exists, so the bill's payments match (decision 99, #338); a text the bill already has is kept as it is. A bill saved under the bank's raw text, before Phase 3.5 (`merchant_raw_text = 1`), still matches a transaction with that raw name, so existing bills keep working; a bill saved since holds a key (`merchant_raw_text = 0`) and matches only a transaction whose key it is. The two never mix: a flagged bill matches only by raw name and a key bill only by key, so an unrelated charge whose merchant name happens to equal an old bank text never matches an old bill, and a key bill never matches a different merchant that merely has the same bank text.
2. **Amount:** it's within ±10% of the occurrence's amount, so a bill that varies a little (like utilities) still matches. An occurrence's amount is its month's: the latest `bill_amounts` row on or before its due month, and `bills.amount_cents` is the current one (§5, decision 101). Status, Safe to spend and "Price changed?" use the same amount.
3. **Date:** it falls within ±5 days of that occurrence's due date, or within ±3 days for a weekly bill only, so two weeks' windows never overlap; every other frequency (monthly, yearly, every-two-weeks and quarterly) keeps ±5 (decision 74). This keeps a late payment from last month from being mistaken for this month's.
4. **Unclaimed:** it isn't already linked to a bill occurrence, isn't a split parent (from Phase 3.5 an excluded payment qualifies, decision 67, unless a person excluded it: the matcher leaves that one, and only a person's hand link takes it; once linked it counts in Spent whatever its exclusion, and the link never changes the exclusion, §8.5), and hasn't been dismissed for this occurrence. From Phase 5 (decision 74, #202) it also isn't a planned expense's payment: a payment pays a bill or a plan, never both (§5), so the matcher skips a plan-linked transaction.

**If several candidates qualify,** the matcher picks the one closest to the due date, then the one closest in amount, then the earliest by `id`, so the result is always the same.

**When matching runs:** after each sync, and after a bill is created, edited or reactivated. It only fills occurrences that have no payment yet and never changes an existing link.

**People override the matcher.** From a bill, a person can link a transaction by hand (`matched_by = user`), choosing which occurrence it pays. For monthly and yearly bills, the picker lists unclaimed transactions (a payment a split change unlinked is listed; see Splits below) within 30 days of the due date, and accepts one only within that window; for weekly bills it is within 3 days, the same window as the matcher, so its windows do not overlap; for every other frequency it stays at 30 days. It orders by same merchant first, then closest amount (decision 60). A person can unlink a wrong match. Unlinking records a `dismissed` row, so the matcher won't pick that transaction for that occurrence again. From Phase 5 (decision 74): a bill saved without a merchant key gets the key of the first payment linked to it by hand; a person can link more than one payment to an occurrence (a bill paid in parts), while the matcher still links one; a payment linked to a bill takes its category as set out in §7.

The amount tolerance (10%) and date window (±5 days) are single config values. The demo seed exercises all the cases: a bill paid on time, one paid 3 days late, and a lookalike charge outside the window that correctly doesn't match.

**Splits:** splitting creates child transactions (`parent_id` set) and marks the parent `is_split = true`. The children must add up exactly to the parent's `amount_cents`, or the split is rejected. If the bank later changes a split purchase's amount, sync removes the split and the purchase goes back to the category it had before it was split (Tally's earlier guess or the person's pick, kept on the purchase while it is split, so no column is needed for it), with a note on it saying the amount changed; the note stays until a person confirms or changes the category, and a merchant rule or a new Jev guess doesn't replace that category meanwhile. With no earlier category it stays in Needs category. A changed date is copied to the parts (decision 62). A refund linked to one of the parts is unlinked, counts on its own date and category again, and its row says why (decision 99): `refund_unlinked_purchase_date` keeps the purchase's date for that sentence until a person links the refund again. A split cash entry has no bank behind it, so its date and amount are edited by a person (§8.4): a new date moves to its parts, and a new amount that no longer matches its parts can't be saved until the parts are corrected, with a field error ("The parts add up to $90.00. Change them to match $100.00."); the split is never reset (decision 79); Change the parts opens the split with the new total and saves the amount, the parts and the panel's other changes together, keeping the split and the links on its parts. Removing a split deletes the children and clears `is_split`; a refund linked to one of the children is unlinked (`refund_of_id` is set to null) and counts on its own date and category again, and the toast says so (decision 60). Splitting a purchase that has linked refunds, or re-splitting one, asks which part each refund goes with, or Not linked (decision 99): a refund chosen for a part moves onto it when the whole refund still fits that part, and a part too small for its chosen refund is refused with the reason, so no answer is saved until every refund has one; the toast says which part each moved refund now counts with, and Not linked unlinks it as before. A part's bill payment is unlinked the same way, so the bill is unpaid again, and the toast names it: "The Costco membership bill for 2026 is no longer paid." (two or more: "2 bills are no longer paid."). Replacing the parts does the same for a part whose amount or category changed; a new part with the same amount and category as an old part keeps that part's bill payment, still linked, and the toast says nothing about it (decision 99). Such an unlink records no dismissal, so the matcher may link the bill again by itself when the payment still matches it, and Link a payment lists it as usual (decision 105). A person's own Not this one on a purchase or one of its parts is never lost: it is kept on the purchase when its part is removed or replaced, and every part the purchase has from then on (its first split, replaced parts or a new split) starts with it, so the matcher never links any of them to that occurrence (decision 105). A person's own link of the purchase or one of its parts to that occurrence, or the Undo after a Not this one, lifts it for the whole purchase, so a later split doesn't copy a choice the person reversed (#340, #427). When the bank's change removes the split, the purchase's note says the same and names the bills that are still unpaid (`split_removed_bills`), until a person confirms or changes its category; a bill whose occurrence is paid again (Paid on Bills, linked payments reaching 90% of its amount, decision 74), by the matcher or by a person's link, drops out of that sentence, and the sentence goes when no bill is left in it (decision 105). A payment linked to the purchase itself is never a part's and stays.

**Exclusions:** transactions flagged `transfer` or `reimbursement` start with `excluded = true`. A person can always toggle it.

## 7. Categorization and merchant names

**Who picks the category, in order of priority:**

1. **A person.** A manual choice sets `category_source = user`, which is never overwritten. The edit panel's tick "Use this category for this merchant from now on" (#353, decision 101), unticked by default, sets `merchants.default_category_id` when a person ticks it and saves; Organize's Yes does the same for its group.
2. **Merchant rule.** If the merchant has a `default_category_id`, apply it (`category_source = merchant_rule`).
3. **A bill** (from Phase 5, #206, decision 93, Q76 A). A payment linked to a bill, by the matcher or by hand, takes its bill's category (`category_source = bill`) when it has none or only one Tally picked (`category_source` empty, `jev` or an earlier `bill`), so a payment Jev sorted before its bill existed, or one a person re-linked to a different bill after a wrong match, ends up in the right bill's category. A category a person chose (`user`) or a merchant rule gave is never replaced. It sits below a person's choice and a merchant rule, which replace it, and above Jev, who is asked only about what is still empty; unlinking the payment leaves the category on it.
4. **Jev.** Make **one** `POST /v1/systemone` call per transaction. Its `questions` map holds a `category` Choice question (options: the household's category list) and one yes/no (Noul) question per allowed flag (`transfer`, `reimbursement`, `income`), which is the bundling pattern Jev's docs recommend. If the category answer's confidence is at or above the threshold, apply it (`category_source = jev`); otherwise leave the category null for review. Each flag is applied on its own confidence check.

The confidence threshold is a single config value, set during Phase 1 after checking Jev's output on the seed data.

**When Jev runs (Phase 1, #12):** only in the nightly job, never while a page loads; from decision 68, also right after each sync, Sync now included, for that sync's new transactions (within the same daily cap), when the household's "Sort right away" switch is on (decision 79); and the exceptions are a transaction a person unticks from a suggested category (from Phase 4, decision 64) and a transaction that still needs a category when a person adds a clearer name or a note to it (decision 79), each asked about again right after the page has answered, with the merchant rules first, so a rule that matches decides it and Jev isn't asked. In the demo it runs right after the reset. The job applies merchant rules to transactions without a person's category choice, including replacing a bill category and Tally's unconfirmed guesses, then asks Jev about the rest: at most 40 calls a day in the demo, and 500 in production (decision 56). The cap is one per household day, midnight to midnight in the household's time zone, shared by the syncs and the night's runs (decision 79). One run also asks about at most 300 transactions, since a call costs about three of the 1,000 queries D1 allows in one invocation. So production's night is three runs, 20 minutes apart (a fourth, at 10:00, sends the due reconnect reminders and asks neither Jev nor Workers AI anything, §4), each its own invocation with the whole limit (§4.1): the 09:00 run syncs the banks and asks Jev and Workers AI nothing, because a sync spends about five queries for each new transaction and 300 calls are about 900 more, and a big sync could leave no queries for names; the 09:20 run asks Jev about up to 200 transactions and then makes the night's names (§7), which together are about 900 queries; and the 09:40 run asks about what the 09:20 run left, at most 300 calls, and makes no names, so the night's last sort never waits on them. A run is cut off at 15 minutes of wall-clock time, so a step that is slow can't use the whole of it: at 09:20 the sort starts no call more than 9 minutes after the run began and the names start no request more than 13 minutes after it began, and at 09:40 the sort starts no call more than 13 minutes after the run began (§7). The calls a run reserved and didn't ask for want of time are given back to the day, and what isn't asked waits for the next run. The day's two passes can reach the 500, so a newly linked bank's backfill of up to 500 can be sorted in a night; when Jev answers slowly, the time budgets stop the passes sooner, and what's left is asked the next night (decision 56). The demo has one run, which does all of it within its much smaller caps. A Cloudflare Queue lifts these limits (#248; decision 90, with the schedule the owner picked in decision 101): the 09:00 run syncs the banks and lines up the transactions waiting to be sorted on the queue, its consumer sorts them in small batches, each its own invocation with its own 1,000 D1 queries at no cost at this size, and the 09:20 run writes the night's guesses (names and new-category suggestions), in both apps; How Tally works lists it as "Cloudflare Queue". Until #248 ships, the three runs above are how the night works. With "Fill in details" on, a transaction that rules or a person already sorted is asked too, once, for its empty details only (§8.6, decision 81). Pending transactions are asked like any other, so they don't sit in Spent; when the bank posts one, Tally's answer moves to the posted transaction with the rest (§6, decision 79). A failure that would hit every call (rate limit, server error, timeout, bad key) stops that run, and the next run retries; a failure about one transaction (Jev rejects it, or answers with something that isn't one of the options) skips just that transaction, which stays pending; three such failures in a row stop the run, since they point at every call. A transaction Jev failed on is asked about last from then on (`jev_failed_at`, decision 31), so it can never block the others. With no categories to offer, Jev isn't asked for a category: a credit is asked first, for its income answer while the "Spot paychecks" switch is on; an outgoing purchase (more than zero) is asked once for its transfer and reimbursement flags while the categories switch is on; and a low answer, kept as `income_confidence` or `transfer_confidence`, or the flag a confident one sets, means it isn't asked again until a category is active. With "Fill in details" on, a call for empty details alone still runs, without the category question (decision 81). The threshold starts at 0.80 and applies to the category's confidence and to each flag's probability. Below the threshold, the category stays empty but its confidence is stored, so Jev isn't asked about the same transaction again (decision 27), except in the cases above, when a person unticks it from a suggested category or adds a clearer name or a note to it. Jev is told the raw name, the merchant's display name (or, when none is chosen, the bank's own store name the row shows, never Tally's guessed name, decision 103), the amount in cents with its direction (money out or in), and the account type. The category question also offers "None of these fit", which never applies a category. Jev's pick is kept in `jev_category_id` either way, next to its confidence, so the threshold can be tuned from real picks (#49). Jev's transfer and reimbursement flags exclude the transaction (§6), which a person can undo with the edit panel's exclude toggle (#27). Jev's income answer is stored (decision 68, replacing decision 28's "not stored") only while the household's "Spot paychecks" switch is on (§8.6) and no person has chosen: at or above the threshold it sets `flag_income` with `income_source = jev`; the edit panel's "Count as income" lets a person correct it, and a person's choice (`income_source = user`) is never overwritten. Below the threshold the flag isn't applied, but Tally keeps its probability, `income_confidence` for income and `transfer_confidence` for a transfer (§5), so the transaction can show "Maybe income" or "Maybe a transfer" (decision 79). The bank's own income mark (a flag Plaid's `INCOME` category set, §5) stands over Tally's answer, and a person overrides both (decision 79). An unreviewed negative credit stays held out of spending until Jev confidently classifies it as non-income or a person marks it reviewed in the edit panel; a person can clear income and mark a credit reviewed in the same save (decision 70). The edit panel shows "Picked by Tally · N% sure" when Jev chose the category; no screen names Jev, which is "Tally" to the people using it, and only the demo's How Tally works page names it, where it explains how Tally is built (decision 64). From Phase 4, Jev's pick below the threshold shows as a suggestion ("Maybe Eating Out"), never applied without a tap (decision 64). Only the log line `jev: <status> <request id>` is ever logged.

**Jev input:** the raw name, merchant display name (or, when none is chosen, the bank's own store name the row shows, never Tally's guessed name, decision 103), amount, account type, and Plaid's own category hint if present (from Phase 2, once sync stores it, #18); from Phase 4, the transaction's note too, so a note can help it sort (decision 64).

**Boundary:** all Jev calls go through one module (`src/ai/categorize.ts`) with one function signature. Switching providers changes only that file.

Jev's income answer never marks money out (a positive amount) as income. A split part counts on its own link or its parent's, since a bank transaction that paid a bill and was split afterwards is still that payment whole; the parent itself never counts once split, so each part counts once. A linked payment is not listed as excluded: the list, Excluded in the Show choice and How Tally works' excluded count leave it out, Show lists it under Spending (a linked credit under Refunds, so Refunds and Excluded never share a row), and its panel says it pays a bill (the Exclude chip still shows the saved exclusion). A payment from the same merchant outside ±10%, and inside the bill's own date window (§6.1 rule 3: ±3 days for weekly, ±5 for the others), is offered as "Price changed? Update the bill" rather than ignored.
- **Merchant:** Plaid's `merchant_name` is stored, and rules, bill matching, refunds and finding bills match on it when present, the raw name otherwise (the merchant key, §6.1). The `merchants` table holds rules and chosen names under the same key, so "TARGET 1234" and "TARGET 5678" share one rule, one name, one bill and one suggested bill, and a hand-entered cash transaction, which has no merchant name, still goes by its raw name. Each merchant has one settings row (rule, name, Not a bill), found by its key, so every bank text that shares a key shares it, and a change a person makes is saved to that row and recategorizes the charges with that key. When Plaid first names a merchant, its row starts as a copy of the row saved under its bank text (made once, at the sync that first names it, before rules run; when several bank texts share the name in one sync, even on different pages, each rule, name and Not a bill comes from the first of their rows that has one), so existing rules, names and Not a bill carry over, and a later edit to the old row never reaches it. A bill saved before this keeps its bank text (`merchant_raw_text = 1`) and still matches it. If Plaid later corrects a transaction's merchant, a category a merchant rule gave it is cleared so the new merchant's rule applies; a person's or Jev's choice stays.
- **Rules after every sync:** merchant rules run at the end of every sync, however it started (the webhook, the daily catch-up, Sync now, or a repaired connection), not only on Sync now and overnight. They run after the copy of a merchant's settings on its first Plaid name and before bills match, and before Jev when Jev runs at sync (§8.6). They replace a bill category and Tally's unconfirmed guesses, but never a person's category choice.
- **Refunds:** linking a refund includes it in the budget; a refund can't be larger than what's left of its purchase, and a purchase is refunded at most to its amount. A split refund counts by its parts, and its parent keeps its link meanwhile; when the split is removed or replaced, that link is checked the same way as a new one and cleared if the whole refund no longer fits, so a bank correction that unlinked some parts can't come back through the parent. A split asks which part a linked refund goes with, or Not linked (decision 99), instead of unlinking it.
- **Bills:** no two active bills with the same name; an amount over $100,000 needs confirming. (A yearly bill already requires its anchor month, in the form and the schema.) Names are compared ignoring A to Z capitals and spaces around them, so "rent" and " RENT " are the same name and "Café" and "CAFÉ" differ, and the form and the write compare them the same way: adding or editing a bill to another active bill's name is a field error under Name, "You already have a bill called Rent."; a bill keeps its own name, and a bill that already shares its name with another (from before this rule) can still be edited as long as its name doesn't change, since only a new name is checked; an inactive bill's name doesn't block an add, and reactivating an inactive bill that would repeat an active one is refused the same way, after which Reactivate also sends what the Name field holds, so renaming the bill is how to get it back. The write repeats the check inside its own statement (no unique index, since a family may already hold duplicates), so two saves at once can't both take a name. "Over" means more than $100,000.00, so exactly that saves without asking. Adding or editing an amount over it comes back unsaved with "$150,000.00 is a lot for a bill." under the amount, and under that alert a "Yes, $150,000.00 is right" chip to tick before Save works (decision 80, P84 A); the tick covers that exact amount only, so changing the amount asks again.
- **A failed save says so:** an htmx error shows "Couldn't save. Check your connection and try again." in `role="alert"`, and the app has its own 404 and 500 pages.
- **A connected bank (not disconnected) that needs attention or hasn't synced for 3 days** is flagged on Home with a link to Accounts, because Safe to spend may be too high: a dashed "as of Oct 2" tag on Safe to spend, and a soft brick-tinted line with a Fix button that opens Accounts, before the forecast (§8.4; the look replaced by decision 82, the job unchanged).
- **The first visit's empty list** says "Importing your transactions…" or "Link a bank to see transactions" rather than "No transactions match".

How each looks was picked on the proposals page (decision 72): "Pending" on the row's caption line, and a line in the panel saying its amount can still change; a "Time zone · Eastern" disclosure row under a Household heading in Settings; "Price changed?" on the bill's row with the payment, and the update offered on the bill's page; the stale-bank line under Home's status sentence, linking to Accounts (its look replaced by decision 82, §8.4); a failed save as an error toast with the alert icon, the sheet left open; the 404 and 500 pages with the ledger drawing and a serif 404 or 500; EmptyState for both first-visit lists; and a bill over $100,000 saved only once a "Yes, $X is right" chip is ticked.

## 10. Errors, security, and operations

| Situation | Behavior |
|---|---|
| Bank link needs re-authentication (`ITEM_LOGIN_REQUIRED` etc.) | Set `plaid_items.status = needs_attention` and show Fix connection, which opens Plaid Link in update mode. The update-mode `link_token` is created when the button is clicked, never ahead of time, because it expires after 30 minutes. |
| Sync fails partway | Save transactions and the new `sync_cursor` together, in one D1 batch. A retry resumes from the last saved cursor, so nothing is duplicated or skipped. |
| Plaid webhook | Plaid signs every webhook, and the Worker checks the signature against Plaid's published key before trusting it. The `Plaid-Verification` header is a JWT: reject it unless `alg` is `ES256`, fetch the key for its `kid` from `/webhook_verification_key/get` (cached), and verify with Web Crypto (ECDSA P-256). `SYNC_UPDATES_AVAILABLE` starts that Item's transaction sync; permanent `ITEM` errors, pending expiration or disconnect, and revoked user permission mark it as needing attention. The webhook path is the only path excluded from Cloudflare Access, via an Access **Bypass** policy scoped to `/webhooks/plaid`. |
| Jev unavailable or slow | Leave the transaction uncategorized; the nightly job retries it (in production the next of its Jev runs). AI calls never block a page. |
| Workers AI unavailable | No suggestion; retried the next night (suggestions are made in the 09:20 run, after that run's Jev pass, within its 100 and until 13 minutes after the run began). |
| Invalid input (split doesn't add up, bad amount) | Re-render the form with a field error (`role="alert"`). |
| Logging | Never log tokens, secrets, or transaction details. |
| Plaid access tokens | Encrypted with AES-GCM (Web Crypto) using `TOKEN_ENCRYPTION_KEY` before they're stored. |
| Backups | D1 Time Travel restores to a point in time. The retention window gets confirmed in Phase 0 and recorded in the README. |
| Security headers | `X-Frame-Options: DENY`, a strict CSP (no inline scripts; Plaid's CDN allow-listed on the Accounts page), and `SameSite=Lax` on any cookie. |
| Form posts from other sites | Rejected with 403 unless the browser shows the post came from this site (`Sec-Fetch-Site: same-origin` or a matching `Origin`), using Hono's built-in `csrf` middleware. |

- **Unit tests (most tests):** cents parsing and formatting, budget math, the bill status rules, split validation, and category priority.

- **E2E (Playwright), critical flows only:** recategorize, split, exclude, and change a budget amount.
- **Screenshots:** on every pull request from this repo, CI screenshots each page at 1280×800 and 390×844, puts them in the PR description, and fails if a page logs a console error.
- **CI (GitHub Actions):** type-check, lint, and tests on every push. A failing check blocks the merge.
- **Deploy:** manual at first, with `npx wrangler deploy --env demo` or `--env production`, documented in the README.
