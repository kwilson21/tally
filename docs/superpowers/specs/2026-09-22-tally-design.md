# Tally — Design Spec

- **Date:** 2026-09-22
- **Status:** Approved by the owner (2026-09-25, Phase 1 review)
- **Owner:** Kazon Wilson

## 1. What Tally is

Tally is a family budgeting app. It pulls in bank transactions automatically, sorts them into categories with a small AI model, and shows the household how much is left to spend this month.

It serves two audiences from one codebase:

1. **The owner's household**: a private app behind a login wall, with real bank data.
2. **The public**: a portfolio demo at `tally-demo.thesuperhuman.us` with fake data only.

Tally replaces the owner's Django app (`personal-finance-app`). That app stays in place until Tally has fully taken over its job.

## 2. Guiding rules

1. **Explainable in one sentence.** Every part of the system must be explainable in one plain sentence, and this spec gives that sentence for each part. If the owner can't explain a part in their own words, it doesn't go in.
2. **The spec is the source of truth.** Nothing gets built unless it's in this spec. New ideas go on the Later list (§12) until the spec is updated.
3. **Decisions stay decided.** Settled choices are recorded in `docs/decisions.md` with their reasons. Reopening one takes a new decision entry, not a silent change.
4. **Simplicity beats keywords.** Tools are picked because they're the simplest fit, not because they appear on job postings.
5. **The server owns all state.** No client-side state framework.
6. **AI suggests; code calculates; people decide.** AI models classify and suggest. Deterministic code does all money math. People can override any AI output.

## 3. Scope

The first seven features ship across phases (§11); the eighth moved to the Later list (decision 66) and came back as receipts, bills and invoices in Phase 6 (decision 137):

| # | Feature |
|---|---|
| 1 | Budget vs. spent this month, with category left and safe to spend |
| 2 | Bills: upcoming, overdue, paid |
| 3 | Transaction list: browse, search, recategorize |
| 4 | Splitting a transaction across categories |
| 5 | Excluding transactions from the budget (transfers, reimbursements, one-offs) |
| 6 | Spending trends: month over month, by category |
| 7 | Account balances and net worth over time |
| 8 | ~~Documents: stored statements and receipts (PDF)~~ Receipts, bills and invoices: Tally reads a receipt, bill or invoice (a photo, a PDF or a forwarded email) and offers what it read on the purchase it belongs to (§8.9, decision 137). A shelf of stored statements stays on the Later list (§12) |

Also in scope: AI-suggested merchant name cleanup (accept or reject), AI-suggested new categories when none of the household's categories fit (a person creates or dismisses them), the demo banner with its Start here link, the three things to try (in How Tally works' Start here, decision 111), a "How it works" page, and onboarding: what a first visit shows and teaches, in the demo and in the family's first week (decision 49, #95).

**Household model:** one shared household. Everyone who can log in sees and edits the same data. Changes record who made them.

**Data:** fresh start. Nothing is migrated from the Django app. Banks are linked again, and Plaid backfills the history.

## 4. Architecture

> One small TypeScript server on Cloudflare builds each page, stores data in a SQLite database, pulls bank data from Plaid, and uses three AI models: Jev for categories, Workers AI for merchant names, and, from Phase 6, Clairic (on Workers AI) for reading receipts.

| Part | Job, in one sentence |
|---|---|
| **Cloudflare Worker (Hono, TypeScript)** | Handles every request: builds pages, receives Plaid webhooks, and runs scheduled jobs. |
| **HTMX** | When you click something, HTMX asks the server for a piece of new HTML and swaps it into the page. |
| **Tailwind CSS** | Styles the pages with utility classes, compiled into one CSS file. |
| **Workers static assets** | Serves the CSS file, `htmx.js`, and icons. |
| **D1 (SQLite)** | Stores all data. |
| **Plaid (REST over `fetch`)** | Supplies accounts, transactions, and balances from the family's banks. |
| **Jev (TypeSafe AI)** | Picks a category and flags for each transaction, with a confidence score. |
| **Workers AI** | Suggests a clean merchant name, which a person accepts or rejects. |
| **Resend** | Sends bank sign-in reminder emails and the first week's ready email; Cloudflare Email Service is the best-effort fallback for destinations verified in Cloudflare Email Routing (decision 86), except for a ready email Resend may already have accepted (decision 146). |
| **Web Push** | Tells a device you turned on that your first questions are ready, 2 minutes after you leave. Tally sends it from the Worker with no other service. |
| **Cron Triggers** | Run the daily bank sync (a backup for webhooks), one bank at a time so one failure doesn't stop the others, skipping any bank that needs reconnecting; then retry uncategorized transactions. Each minute, in the family app, it checks whether a new family's first questions have opened, pushes each device of a person who left the page 2 minutes ago (decision 148), and emails each person who left the page 10 minutes ago, once; the 10:00 run sends due reconnect reminders and checks again. The demo has no bank sync or email: each night it resets to the seed data, then retries uncategorized transactions. |
| **Cloudflare Workflows** | Sorts transactions with Jev in small steps and keeps each answer for a few days, so a step that has to run again doesn't ask twice. |
| **Cloudflare Access** | A login wall with the family's emails in front of the family app; the app has no login code of its own. |
| **Wrangler** | The command-line tool that deploys the Worker and stores secrets. |

| Jev | On | On |

From Phase 6, Clairic reads the seed's sample receipts when a visitor taps one (§8.9). |
| Resend | On (`RESEND_API_KEY` secret) | Off; no binding or secret. |
| Login | Cloudflare Access | Public, with a demo banner on every page |
| Nightly job | Two production runs, each its own Worker invocation (§7), and a third each minute, the ready push and then the ready email (decisions 146 and 148). 09:00, sync, then the night's Workflow (sort everything waiting, then names and new-category suggestions, then the first night's counts), then the feedback retry; 10:00, due reconnect reminder emails, the first week's ready push and ready email as a backstop (decisions 146 and 148) and, from Phase 6, another try at up to 20 emailed receipts Clairic couldn't read when they came (§8.9), kept out of the 09:00 run so their queries never compete. | One run, 09:00: reset the database and bucket to the seed, then start the night's Workflow (categorize up to 40 calls, then name suggestions, up to 100, none started more than 13 minutes after their step began), then the feedback retry. It never sends email. |

The account is on Workers Paid (decision 90), which the nightly design relies on: 1,000 D1 queries per invocation (50 on Free), long scheduled runs, room for more Cron Triggers than Free's 5, and Cloudflare Workflows, whose included steps cover Tally's sorting (decision 139).

**How real data stays out of the demo:** the demo database is only ever built from seed files in the repo. The demo environment has no Plaid credentials and no binding to the production database or bucket, so no code path can reach real data.

### 4.2 Secrets

Secrets are stored with `wrangler secret put` and never committed. The owner enters every value.

| Secret | production | demo |
|---|---|---|
| `PLAID_CLIENT_ID`, `PLAID_SECRET` | yes | no |
| `TOKEN_ENCRYPTION_KEY` (encrypts Plaid access tokens) | yes | no |
| `PLAID_WEBHOOK_URL` (plain config, not secret) | yes | no |
| `PLAID_ENV` (plain config: `sandbox` or `production`; anything else means sandbox) | yes | no |
| `JEV_API_KEY` | yes | yes |
| `RESEND_API_KEY` | yes | no |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (Web Push, decision 148: the public key is an uncompressed P-256 point and the private key its scalar, both base64url) | yes | no |

Receipts (Phase 6, decision 137) add no secret: Clairic runs on the `AI` binding, R2 on the `DOCS` binding, and email arrives through an Email Routing rule.

Local development uses a git-ignored `.dev.vars` file, with Plaid **Sandbox** keys only (decision 36); tests fake Plaid at `fetch`, and production keys exist only as secrets on the production Worker. The repo commits a `.dev.vars.example` with placeholder names only.

## 6. Money rules and budget math

**Sign convention (Plaid's):** a positive amount is money out, and a negative amount is money in. Account balances on debt accounts (`is_liability`) display as negative.

**Dates:** transaction dates are stored and compared exactly as Plaid sends them (`YYYY-MM-DD`), with no time-zone conversion. A month is the `YYYY-MM` prefix of the date. "Today", which decides the current month and bill status, is the household's date in its time zone, a Settings choice that starts as Eastern (`America/New_York`); a transaction's own date is never converted (decision 67).

**Pending (decision 67):** a pending transaction counts like any other and shows the word "Pending". When the bank posts it under a new id, the person's category, note, exclusion and every link (bill, refund, counts in) move to the posted transaction, and so do Tally's own answer (§7, decision 79) and a split if the amount is unchanged; if the posted amount differs, the split is removed as in §6.1 (decision 62). A pending one the bank drops is removed with its links.

"Counted transactions" for a month means: date in that month (or, from Phase 3, a payment linked to an earlier month's bill occurrence counts in that occurrence's month instead, never both; decision 58, #26; and a refund linked to its purchase counts in the purchase's counted month and current category instead of its own, never both, while the purchase counts; if the purchase is excluded, even one that counts only because it pays a bill, the refund counts on its own date and category again; a refund of a split purchase links to one of its parts, decision 60), `excluded = false` (or a payment linked to a bill or a planned expense, which counts whatever its exclusion, §6.1 rule 4 and §8.4), and `is_split = false`, so split parents are skipped and their children count instead. An unreviewed negative bank credit (`COALESCE(credit_reviewed, 0) = 0`, not flagged as income) is held out of Spent, Uncategorized, and Safe to spend until Jev confidently categorizes it as non-income or a person marks it reviewed as a refund or other non-income credit (decision 70). Transactions flagged `income` are counted only toward **Income** and are left out of Spent, Uncategorized, and Safe to spend. A refund that follows its purchase has no category of its own to set, so only the purchase shows Needs category; its amount stays in Uncategorized until the purchase has a category.

### 6.1 Matching bills to payments

> The matcher gives each bill occurrence at most one payment, and each transaction pays at most one bill. (From Phase 5, decision 74: a person can link several payments to one occurrence, a bill paid in parts; the matcher still links one, and each transaction still pays at most one bill or one planned expense, never both.)

**The key:** a bill *occurrence* is identified by `(bill_id, period)`, where `period` is `YYYY-MM` for monthly bills and `YYYY` for yearly bills; from Phase 5 (decision 74), a weekly or every-two-weeks occurrence's own due date (`YYYY-MM-DD`) and a quarterly one's `YYYY-Qn`, the calendar quarter that holds its due date (Q1 is January to March; decision 79), so each key names exactly one occurrence. Unique constraints in `bill_payments` let the database itself rule out double matches in either direction, so re-running the matcher changes nothing. (From Phase 5 the one on (`bill_id`, `period`) is dropped for parts paid by hand, and the matcher instead skips any occurrence that already has a linked payment.)

**A transaction is a candidate for a bill occurrence only if all of these hold:**
1. **Merchant:** its merchant key equals the bill's. A transaction's merchant key is Plaid's `merchant_name` when present, otherwise its `raw_name`; a bill's is the key of the payment it was made from or linked to (from Phase 3.5, decision 67; before that, `raw_name` against `merchant_raw_name`). A bank text typed for a bill is saved as the key of the newest transaction whose raw name it is, when one exists, so the bill's payments match (decision 99, #338); a text the bill already has is kept as it is. A bill saved under the bank's raw text, before Phase 3.5 (`merchant_raw_text = 1`), still matches a transaction with that raw name, so existing bills keep working; a bill saved since holds a key (`merchant_raw_text = 0`) and matches only a transaction whose key it is. The two never mix: a flagged bill matches only by raw name and a key bill only by key, so an unrelated charge whose merchant name happens to equal an old bank text never matches an old bill, and a key bill never matches a different merchant that merely has the same bank text.
2. **Amount:** it's within ±10% of the occurrence's amount, so a bill that varies a little (like utilities) still matches. An occurrence's amount is its month's: the latest `bill_amounts` row on or before its due month, and `bills.amount_cents` is the current one (§5, decision 101). Status, Safe to spend and "Price changed?" use the same amount.
3. **Date:** it falls within ±5 days of that occurrence's due date, or within ±3 days for a weekly bill only, so two weeks' windows never overlap; every other frequency (monthly, yearly, every-two-weeks and quarterly) keeps ±5 (decision 74). This keeps a late payment from last month from being mistaken for this month's.
4. **Unclaimed:** it isn't already linked to a bill occurrence, isn't a split parent (from Phase 3.5 an excluded payment qualifies, decision 67, unless a person excluded it: the matcher leaves that one, and only a person's hand link takes it; once linked it counts in Spent whatever its exclusion, and the link never changes the exclusion, §8.5), and hasn't been dismissed for this occurrence. From Phase 5 (decision 74, #202) it also isn't a planned expense's payment: a payment pays a bill or a plan, never both (§5), so the matcher skips a plan-linked transaction.

**If several candidates qualify,** the matcher picks the one closest to the due date, then the one closest in amount, then the earliest by `id`, so the result is always the same.

**When matching runs:** after each sync, and after a bill is created, edited or reactivated. It only fills occurrences that have no payment yet and never changes an existing link.

**People override the matcher.** From a bill, a person can link a transaction by hand (`matched_by = user`), choosing which occurrence it pays. For monthly and yearly bills, the picker lists unclaimed transactions (a payment a split change unlinked is listed; see Splits below) within 30 days of the due date, and accepts one only within that window; for weekly bills it is within 3 days, the same window as the matcher, so its windows do not overlap; for every other frequency it stays at 30 days. It orders by same merchant first, then closest amount (decision 60). It shows the five closest as rows with the transaction row's look, each a 44px radio, then "Show all N charges", which opens the rest in the same order (decision 126, P138 A, #645). A person can unlink a wrong match. Unlinking records a `dismissed` row, so the matcher won't pick that transaction for that occurrence again. From Phase 5 (decision 74): a bill saved without a merchant key gets the key of the first payment linked to it by hand; a person can link more than one payment to an occurrence (a bill paid in parts), while the matcher still links one; a payment linked to a bill takes its category as set out in §7.

The amount tolerance (10%) and date window (±5 days) are single config values. The demo seed exercises all the cases: a bill paid on time, one paid 3 days late, and a lookalike charge outside the window that correctly doesn't match.

**Splits:** splitting creates child transactions (`parent_id` set) and marks the parent `is_split = true`. The children must add up exactly to the parent's `amount_cents`, or the split is rejected. If the bank later changes a split purchase's amount, sync removes the split and the purchase goes back to the category it had before it was split (Tally's earlier guess or the person's pick, kept on the purchase while it is split, so no column is needed for it), with a note on it saying the amount changed; the note stays until a person confirms or changes the category, and a merchant rule or a new Jev guess doesn't replace that category meanwhile. With no earlier category it stays in Needs category. A changed date is copied to the parts (decision 62). A refund linked to one of the parts is unlinked, counts on its own date and category again, and its row says why (decision 99): `refund_unlinked_purchase_date` keeps the purchase's date for that sentence until a person links the refund again. A split cash entry has no bank behind it, so its date and amount are edited by a person (§8.4): a new date moves to its parts, and a new amount that no longer matches its parts can't be saved until the parts are corrected, with a field error ("The parts add up to $90.00. Change them to match $100.00."); the split is never reset (decision 79); Change the parts opens the split with the new total and saves the amount, the parts and the panel's other changes together, keeping the split and the links on its parts. Removing a split deletes the children and clears `is_split`; a refund linked to one of the children is unlinked (`refund_of_id` is set to null) and counts on its own date and category again, and the toast says so (decision 60). Splitting a purchase that has linked refunds, or re-splitting one, asks which part each refund goes with, or Not linked (decision 99): a refund chosen for a part moves onto it when the whole refund still fits that part, and a part too small for its chosen refund is refused with the reason, so no answer is saved until every refund has one; the toast says which part each moved refund now counts with, and Not linked unlinks it as before. A part's bill payment is unlinked the same way, so the bill is unpaid again, and the toast names it: "The Costco membership bill for 2026 is no longer paid." (two or more: "2 bills are no longer paid."). Replacing the parts does the same for a part whose amount or category changed; a new part with the same amount and category as an old part keeps that part's bill payment, still linked, and the toast says nothing about it (decision 99). Such an unlink records no dismissal, so the matcher may link the bill again by itself when the payment still matches it, and Link a payment lists it as usual (decision 105). A person's own Not this one on a purchase or one of its parts is never lost: it is kept on the purchase when its part is removed or replaced, and every part the purchase has from then on (its first split, replaced parts or a new split) starts with it, so the matcher never links any of them to that occurrence (decision 105). A person's own link of the purchase or one of its parts to that occurrence, or the Undo after a Not this one, lifts it for the whole purchase, so a later split doesn't copy a choice the person reversed (#340, #427). When the bank's change removes the split, the purchase's note says the same and names the bills that are still unpaid (`split_removed_bills`), until a person confirms or changes its category; a bill whose occurrence is paid again (Paid on Bills, linked payments reaching 90% of its amount, decision 74), by the matcher or by a person's link, drops out of that sentence, and the sentence goes when no bill is left in it (decision 105). A payment linked to the purchase itself is never a part's and stays.

**Exclusions:** transactions flagged `transfer` or `reimbursement` start with `excluded = true`. A person can always toggle it.

## 7. Categorization and merchant names

**Who picks the category, in order of priority:**

1. **A person.** A manual choice sets `category_source = user`, which is never overwritten. The edit panel's tick "Use this category for this merchant from now on" (#353, decision 101), unticked by default, sets `merchants.default_category_id` when a person ticks it and saves; Organize's Yes does the same for its group.
2. **Merchant rule.** If the merchant has a `default_category_id`, apply it (`category_source = merchant_rule`).
3. **A bill** (from Phase 5, #206, decision 93, Q76 A). A payment linked to a bill, by the matcher or by hand, takes its bill's category (`category_source = bill`) when it has none or only one Tally picked (`category_source` empty, `jev` or an earlier `bill`), so a payment Jev sorted before its bill existed, or one a person re-linked to a different bill after a wrong match, ends up in the right bill's category. A category a person chose (`user`) or a merchant rule gave is never replaced. It sits below a person's choice and a merchant rule, which replace it, and above Jev, who is asked only about what is still empty; unlinking the payment leaves the category on it.
4. **Jev.** Make **one** `POST /v1/systemone` call per transaction. Its `questions` map holds a `category` Choice question (options: the household's category list) and one yes/no (Noul) question per allowed flag (`transfer`, `reimbursement`, `income`), which is the bundling pattern Jev's docs recommend. If the category answer's confidence is at or above the threshold, apply it (`category_source = jev`); otherwise leave the category null for review. Each flag is applied on its own confidence check.

The confidence threshold is a single config value, set during Phase 1 after checking Jev's output on the seed data.

**When Jev runs (Phase 1, #12):** only in the nightly job, never while a page loads; from decision 68, also right after each sync, Sync now included, for that sync's new transactions (within the same daily cap), when the household's "Sort right away" switch is on (decision 79); and the exceptions are a transaction a person unticks from a suggested category (from Phase 4, decision 64) and a transaction that still needs a category when a person adds a clearer name or a note to it (decision 79), each asked about again right after the page has answered, with the merchant rules first, so a rule that matches decides it and Jev isn't asked. In the demo it runs right after the reset. The job applies merchant rules to transactions without a person's category choice, including replacing a bill category and Tally's unconfirmed guesses, then asks Jev about the rest: at most 40 calls a day in the demo, and 500 in production (decision 56), or, in production until pay, bills and budgets are all answered, 2,000 for each connected bank (decision 146). The cap is one per household day, midnight to midnight in the household's time zone, shared by the syncs and the night (decision 79). Production's night is one run at 09:00 (a second, at 10:00, sends the due reconnect reminders and the first week's ready email and asks neither Jev nor Workers AI anything, §4): it syncs the banks, then starts one Cloudflare Workflow (#248, decision 139, in place of the Queue of decisions 90 and 101), which sorts everything waiting in groups of 25, one save a group, then makes the night's notes and names (§7), then the new-category suggestions, then keeps the first night's counts (§8.8). Each is a step of its own, and a step that fails is logged by its error's name while the next one still runs. The names and the suggestions each start no request more than 13 minutes after their step began, so a slow Workers AI ends inside the step's 15-minute timeout, and neither step is ever run twice, so no request is made twice. A Workflow has no per-invocation query limit like a cron run's, so the night asks about everything waiting, up to the day's cap: a first week's backfill, up to 2,000 a connected bank, can be sorted in a night, one instance asking at most 5,000 calls (decision 146), and what the cap leaves is asked the next day (decision 56). The night ignores "Sort right away", as before. The sorting after each sync and "ask again" run on the same Workflow (§8.6); How Tally works lists it as "Cloudflare Workflows". The demo has the same one run, after its reset, within its much smaller caps. With "Fill in details" on, a transaction that rules or a person already sorted is asked too, once, for its empty details only (§8.6, decision 81). Pending transactions are asked like any other, so they don't sit in Spent; when the bank posts one, Tally's answer moves to the posted transaction with the rest (§6, decision 79). A failure that would hit every call (rate limit, server error, timeout, bad key) stops that run, and the next run retries, except in the sorting Workflow: there a rate limit, an overload, a server error or no response (a timeout) waits and asks again (30 seconds, doubling up to 16 minutes, or Jev's `retry-after` up to 30 minutes, at most six waits in a row and 60 minutes in one run), and a bad key still stops the run at once (decision 145); a failure about one transaction (Jev rejects it, or answers with something that isn't one of the options) skips just that transaction, which stays pending; three such failures in a row stop the run, since they point at every call. A transaction Jev failed on is asked about last from then on (`jev_failed_at`, decision 31), so it can never block the others. With no categories to offer, Jev isn't asked for a category: a credit is asked first, for its income answer while the "Spot paychecks" switch is on; an outgoing purchase (more than zero) is asked once for its transfer and reimbursement flags while the categories switch is on; and a low answer, kept as `income_confidence` or `transfer_confidence`, or the flag a confident one sets, means it isn't asked again until a category is active. With "Fill in details" on, a call for empty details alone still runs, without the category question (decision 81). The threshold starts at 0.80 and applies to the category's confidence and to each flag's probability. Below the threshold, the category stays empty but its confidence is stored, so Jev isn't asked about the same transaction again (decision 27), except in the cases above, when a person unticks it from a suggested category or adds a clearer name or a note to it. Jev is told the raw name, the merchant's display name (or, when none is chosen, the bank's own store name the row shows, never Tally's guessed name, decision 103), the amount in cents with its direction (money out or in), and the account type. The category question also offers "None of these fit", which never applies a category. Jev's pick is kept in `jev_category_id` either way, next to its confidence, so the threshold can be tuned from real picks (#49). Jev's transfer and reimbursement flags exclude the transaction (§6), which a person can undo with the edit panel's exclude toggle (#27). Jev's income answer is stored (decision 68, replacing decision 28's "not stored") only while the household's "Spot paychecks" switch is on (§8.6) and no person has chosen: at or above the threshold it sets `flag_income` with `income_source = jev`; the edit panel's "Count as income" lets a person correct it, and a person's choice (`income_source = user`) is never overwritten. Below the threshold the flag isn't applied, but Tally keeps its probability, `income_confidence` for income and `transfer_confidence` for a transfer (§5), so the transaction can show "Maybe income" or "Maybe a transfer" (decision 79). The bank's own income mark (a flag Plaid's `INCOME` category set, §5) stands over Tally's answer, and a person overrides both (decision 79). An unreviewed negative credit stays held out of spending until Jev confidently classifies it as non-income or a person marks it reviewed in the edit panel; a person can clear income and mark a credit reviewed in the same save (decision 70). The edit panel shows "Picked by Tally · N% sure" when Jev chose the category; no screen names Jev, which is "Tally" to the people using it, and only the demo's How Tally works page names it, where it explains how Tally is built (decision 64). **How the pages behave:**
- **Edits:** an edit returns the updated fragment, plus an `HX-Trigger` header with `toast` and `announce` keys for the confirmation toast and screen-reader announcement.
- **Edit panel and every other sheet:** a modal dialog through `sheet.js` (#87, decision 109): Escape, the backdrop and Cancel all close it the way Cancel does (the page is drawn again with focus back on whatever opened the sheet: its row, or a button such as Add cash or Add a bill), and focus stays inside while it is open, along with an Undo toast on screen. Without the script it is a page region: focus moves into it, and Cancel or the backdrop closes it.
- **Enhancements (decision 45):** swipe gestures, drag and modal dialogs, as in the original app, each built through the catalog with its own allowed-JS decision. Every page works without them. Decision 109 approved the sheet script (#87) and keyboard shortcuts (#72).
- **Charts:** the server renders them as inline SVG. No chart library.
- **Expand and collapse:** `<details>` / `<summary>`. No JavaScript.
- **Motion (decision 76, P74 A):** CSS only. A switch's knob slides, a sheet rises with its backdrop fading in (on desktop the side panel slides in from the right in 200 ms, its backdrop fading in; decision 80, P85 A), and a toast fades and rises, each in 150 to 200 ms; between pages the browser's own View Transitions cross-fade (`@view-transition { navigation: auto; }`), and a browser without them just switches pages. Under reduced motion everything shows its end state. Durations are tokens in `app.css`, and the older animations (the budget bar's fill, a field's shake, the busy ring) move onto the same tokens (decision 79). Every motion is written into its component's use spec.
- **Corners (decision 76, P75 A):** buttons, fields and the sheet are drawn as squircles (`corner-shape: squircle` on the two radius tokens), where the browser supports it; Safari and Firefox keep today's round corners until they do. Chips and the round ticks stay pills (`rounded-full`). The money input's box and cent arrows use `rounded-control` like every input, so they are squircles too (decision 85).
- **JavaScript:** the only custom JavaScript is Plaid Link (loaded from Plaid's CDN, as Plaid requires), a small toast listener, the money input's `money.js` (decision 39), the feedback form's `feedback-privacy.js` and `feedback-diagnostics.js` (decision 61), `keyboard.js` (#72) and the sheet script `sheet.js` (#87) (decision 109). Without `money.js` the money input is a plain field; without `keyboard.js` or `sheet.js` every page works as a plain page. The design system catalog has one script of its own, served only on its pages (decision 44).
- **Keyboard shortcuts (#72, decisions 109 and 118):** `/` moves focus to search; `?` opens the list of keys; `j` and `k` move between the rows of a list, and `e` or Enter opens the row they landed on; on Home, ← and → go to the previous and next month, except while focus is in a region that scrolls sideways (the month-end chart's focusable scroll region, src/views/month-end.tsx), where the arrows scroll it as the browser does; and `u` undoes the last change while its Undo toast shows (#516). None acts while focus is in a field, with Ctrl, Alt or Cmd held, or while another sheet is open (Escape belongs to the sheet script). `?` opens the list as a sheet (the sheet script, decision 109); without the script the same list is a `<details>` at the foot of each desktop page that has How this works, and below 1024px More's contents list ends in a Keyboard shortcuts row that opens the same list. Key chips use a monospaced face, a font token used only for keys. Signed off in the catalog as P128 C before it is built.
- **Accessibility:** every form is labeled, focus rings use `focus-visible`, touch targets are at least 44×44 px, and every HTMX swap is announced: through an `aria-live="polite"` count or announcer, or by moving focus (a whole list is never a live region, which would read out every row). Errors use `role="alert"`.

Generated design studies (phone 390×844, desktop 1280×800) are selected by the owner before a new screen's UI code. They're composition references only; the real UI comes from the design system. The selected direction is "Quiet ledger"; see `docs/design-concepts/README.md` and decisions 20–21.

**Design system catalog (decisions 42–44, 47):** `/design-system` shows every component in its states, rendered by importing the real components with fake data, so the catalog can't drift from the app. It exists in the demo and in development, and production returns 404. Each component is marked with one tier: **Visual** (static states side by side, inert), **Interactive** (works in the browser without the server) or **Flow** (a multi-step journey on fake data, on its own page, with the step in the URL). Every UI change starts there and the owner signs it off there before it reaches an app page. A proposal that changes how something looks is decided by seeing it: `/design-system/proposals` shows each open proposal next to today's version at 1280 and 390, and lists what's been decided, with the issue each ships in (decision 47). Proposed versions are prototypes that live only on that page until the owner picks. The process is in `DESIGN.md`; the inventory of the original app's components is in `docs/design-system/inventory.md`.

### 8.5 Numbers you can trust (decision 67)

Before more Phase 4 features, the rule gaps that can make the family's numbers wrong are fixed (`docs/reviews/original-app-gaps.md` section A, plus B4, C1 and C9). Each fix states its rule here first.
- **Income:** a person can mark or unmark a transaction as income from the edit panel, and a person's choice always wins over later syncs; Plaid's own INCOME category marks money coming in as income at sync only when no person has chosen (the other session's #149/#153 hold unreviewed credits out of spending). A transaction stored with INCOME before that won't come through sync again, so migration 0021 marks those once, by the same rule: only ones nobody has decided (no `income_source`, no person's credit review), with `income_source` left null.
- **Pending:** counted and marked, as in §6.
- **Transfers and card payments:** Plaid's TRANSFER_IN, TRANSFER_OUT and LOAN_PAYMENTS categories exclude a transaction at sync (`excluded_source = 'plaid'`), which a person can undo; Jev still decides the rest. This holds each time Plaid sends the transaction, new, sent again or modified: a person's choice (`excluded_source = 'user'`, an include as much as an exclude) is never changed; a transaction Plaid now calls one of the three is excluded unless something already excludes it (Jev's or an older exclusion keeps its source, also when the bank posts a pending transaction Jev excluded: its exclusion moves onto the posted one even if Plaid excluded that one, whichever way the two reach Tally, §6); and one that stops being one is counted again (`excluded = 0`, no source) only if Plaid excluded it, so Jev's and a person's exclusions stay. A payment linked to a bill is excluded like any other, and counts in Spent all the same (see Bill matching), so removing its link leaves its exclusion as it was. A credit a person decided about is not excluded this way: income they chose or a credit they reviewed, since their choice about what it is wins (decision 70); marking an excluded credit as income, or reviewing it as a refund or other non-income credit, in the edit panel also lifts Plaid's exclusion of it, whatever the Exclude chip showed; reviewing a split credit from its own panel reviews its parts too (a part that is income keeps that, and so does one a person or Jev excluded), since only the parts count. A split's parts follow the bank transaction by the same rule, since the budget counts the parts. How Tally works counts a Plaid exclusion with the transfers. Jev is only asked about counted transactions, so it never clears a Plaid exclusion; one that counts only because it pays a bill is asked for its category alone, so Jev's transfer, reimbursement and income answers never change its exclusion or take it out of Spent. Jev's income answer never marks money out (a positive amount) as income. When this ships it is applied once to transactions already stored (migration `0020`), leaving anything a person or Tally decided as it is; a bill payment is excluded too, but it counts while it's linked, so nothing it paid changes (decision 77's aim).
- **Today:** the household's time zone, as in §6. Settings' Household group offers the six US zones by their everyday names (Eastern, Central, Mountain, Pacific, Alaska, Hawaii) and four others by city (Phoenix, Puerto Rico, Toronto, London); only one of those is saved, a refused value changes nothing, and saving changes only "today", never a transaction's own date.
- **Bill matching:** an excluded payment can still pay a bill, by hand or by the matcher (never one a person excluded, which only a person's hand link takes). A payment linked to a bill counts in Spent, in budgets and in Trends even if a rule, Jev or a person excluded it, so the bill counts once; this is decided when spending is read, so linking and unlinking never write the transaction's exclusion, and removing the link leaves it excluded as it was. A split part counts on its own link or its parent's, since a bank transaction that paid a bill and was split afterwards is still that payment whole; the parent itself never counts once split, so each part counts once. A linked payment is not listed as excluded: the list, Excluded in the Show choice and How Tally works' excluded count leave it out, Show lists it under Spending (a linked credit under Refunds, so Refunds and Excluded never share a row), and its panel says it pays a bill (the Exclude chip still shows the saved exclusion). A payment from the same merchant outside ±10%, and inside the bill's own date window (§6.1 rule 3: ±3 days for weekly, ±5 for the others), is offered as "Price changed? Update the bill" rather than ignored.
- **Merchant:** Plaid's `merchant_name` is stored, and rules, bill matching, refunds and finding bills match on it when present, the raw name otherwise (the merchant key, §6.1). The `merchants` table holds rules and chosen names under the same key, so "TARGET 1234" and "TARGET 5678" share one rule, one name, one bill and one suggested bill, and a hand-entered cash transaction, which has no merchant name, still goes by its raw name. Each merchant has one settings row (rule, name, Not a bill), found by its key, so every bank text that shares a key shares it, and a change a person makes is saved to that row and recategorizes the charges with that key. When Plaid first names a merchant, its row starts as a copy of the row saved under its bank text (made once, at the sync that first names it, before rules run; when several bank texts share the name in one sync, even on different pages, each rule, name and Not a bill comes from the first of their rows that has one), so existing rules, names and Not a bill carry over, and a later edit to the old row never reaches it. A bill saved before this keeps its bank text (`merchant_raw_text = 1`) and still matches it. If Plaid later corrects a transaction's merchant, a category a merchant rule gave it is cleared so the new merchant's rule applies; a person's or Jev's choice stays.
- **Rules after every sync:** merchant rules run at the end of every sync, however it started (linking a bank, the webhook, the daily catch-up, Sync now, or a repaired connection), not only on Sync now and overnight. They run after the copy of a merchant's settings on its first Plaid name and before bills match, and before Jev when Jev runs at sync (§8.6). They replace a bill category and Tally's unconfirmed guesses, but never a person's category choice.
- **Refunds:** linking a refund includes it in the budget; a refund can't be larger than what's left of its purchase, and a purchase is refunded at most to its amount. A split refund counts by its parts, and its parent keeps its link meanwhile; when the split is removed or replaced, that link is checked the same way as a new one and cleared if the whole refund no longer fits, so a bank correction that unlinked some parts can't come back through the parent. A split asks which part a linked refund goes with, or Not linked (decision 99), instead of unlinking it.
- **Bills:** no two active bills with the same name; an amount over $100,000 needs confirming. (A yearly bill already requires its anchor month, in the form and the schema.) Names are compared ignoring A to Z capitals and spaces around them, so "rent" and " RENT " are the same name and "Café" and "CAFÉ" differ, and the form and the write compare them the same way: adding or editing a bill to another active bill's name is a field error under Name, "You already have a bill called Rent."; a bill keeps its own name, and a bill that already shares its name with another (from before this rule) can still be edited as long as its name doesn't change, since only a new name is checked; an inactive bill's name doesn't block an add, and reactivating an inactive bill that would repeat an active one is refused the same way, after which Reactivate also sends what the Name field holds, so renaming the bill is how to get it back. The write repeats the check inside its own statement (no unique index, since a family may already hold duplicates), so two saves at once can't both take a name. "Over" means more than $100,000.00, so exactly that saves without asking. Adding or editing an amount over it comes back unsaved with "$150,000.00 is a lot for a bill." under the amount, and under that alert a "Yes, $150,000.00 is right" chip to tick before Save works (decision 80, P84 A); the tick covers that exact amount only, so changing the amount asks again.
- **A failed save says so:** an htmx error shows "Couldn't save. Check your connection and try again." in `role="alert"`, and the app has its own 404 and 500 pages.
- **A connected bank (not disconnected) that needs attention or hasn't synced for 3 days** is flagged on Home with a link to Accounts, because Safe to spend may be too high: a dashed "as of Oct 2" tag on Safe to spend, and a soft brick-tinted line with a Fix button that opens Accounts, before the forecast (§8.4; the look replaced by decision 82, the job unchanged).
- **The first visit's empty list** says "Importing your transactions…" or "Link a bank to see transactions" rather than "No transactions match".

How each looks was picked on the proposals page (decision 72): "Pending" on the row's caption line, and a line in the panel saying its amount can still change; a "Time zone · Eastern" disclosure row under a Household heading in Settings; "Price changed?" on the bill's row with the payment, and the update offered on the bill's page; the stale-bank line under Home's status sentence, linking to Accounts (its look replaced by decision 82, §8.4); a failed save as an error toast with the alert icon, the sheet left open; the 404 and 500 pages with the ledger drawing and a serif 404 or 500; EmptyState for both first-visit lists; and a bill over $100,000 saved only once a "Yes, $X is right" chip is ticked.

### 8.6 AI that earns its place (decisions 68, 79 and 80)

- **A greyed "Sort right away".** It is greyed out, with "Needs Guess categories or Spot paychecks on", while both of those are off (decision 79). - **Catching up.** A switch turned back on catches up overnight: the next night's Workflow asks about what Tally skipped while it was off, within the daily cap (decision 79): Jev first, then the names, within their step's 13 minutes (§7), so a long list of skipped names may take more than one night.

It runs in the background after the sync's answer, so it never delays or fails a sync. Each group reads what it needs from D1 once, asks Jev about each transaction as a step of its own, whose answer Cloudflare keeps for 3 days without showing it in its dashboard or logs, then saves every answer in one D1 batch, all of them or none. ### 8.9 Receipts, bills and invoices (Phase 6, decision 137)

Tally reads a receipt, bill or invoice with Clairic, Cloudflare's extraction model, and offers what it read on the purchase it belongs to; nothing changes a number until a person keeps it. This brings back the original app's receipt design (RECEIPT-01, Feb 2026), its document model and its issues #21, #8 and #23, and looks at how the Fetch app takes in purchases; `docs/reviews/receipts-original-coverage.md` lists every detail of them and where each one went. It is built in steps, in order, after a spike (§13 item 10), and each step is drawn on the proposals page and picked by the owner before it's built (DESIGN.md's process). Words in quotes say what a screen does; the design step picks the real words. Phase 6 adds three rows to §4's parts table, each in the build that ships it, since How Tally works quotes that table word for word: "Clairic (Workers AI)" reads a receipt, bill or invoice into typed values, each with a confidence score, which a person keeps or changes; "R2" holds the photos, PDFs and email text of the receipts the family keeps; and "Email Routing" receives the receipts and bills the family forwards to the household's receipts address.

**Shared by every step**
- **One module.** Every Clairic call goes through `src/ai/read-receipt.ts`, with one function signature, as Jev's go through `src/ai/categorize.ts`, so switching models changes only that file. It runs on the `AI` binding (`@cf/cloudflare/clairic`), one call per receipt, given either up to four photos (a long receipt in parts) or the receipt's text, and asks for a fixed set of typed fields: the date; the total, subtotal, tax, tip, discount and any amount refunded (numbers with two decimals, in dollars); the payment card's last four digits (a whole number, kept as four digits so 0042 stays 0042); the store, the order or invoice number, and the currency printed beside the total (text); the items as two lists, names and amounts, leaving out tax, tip and discounts (the original's extraction rules); and for a bill, the amount due, the due date, and any amount already paid and the date it was paid. Its `reference_date` is the date the document came: an emailed one's Date header, otherwise the household's today (§6, decision 67), so a date printed without a year reads as the right one. Only the purchase date is corrected after: read as later than the document's date, it's taken as the year before, since a purchase can't come after its receipt (a Dec 31 receipt sent in January is last year's). A due date or a paid date is never moved.
- **What a photo can give (UNVERIFIED).** Clairic's text answers are pieces of the text it was given, and Cloudflare's own photo example reads only numbers and dates. Until the spike shows otherwise, a photo is trusted for the date, the amounts and the card's last four, and the store comes from the bank charge the receipt belongs to, or from what a person types; item names from a photo wait on the same check. A forwarded email, or a PDF with real text in it, gives everything, items included, because its text is read with it.
- **US dollars only.** A receipt whose currency reads as anything but US dollars (a symbol or code other than $, US$ or USD) makes no cash entry, finds no charge and offers no split; its review says it's in another currency, and it can only be kept as a file (other currencies are on the Later list). When no currency can be read (a photo, until the spike shows a photo gives text), the review shows the amounts as US dollars and keeping them says so.
- **Purchases only.** Clairic also reads any amount refunded. A receipt that shows one, or whose total is below zero, is a return: it makes no cash entry, finds no charge and offers no split, and its review says Tally doesn't read returns yet (they're on the Later list); it can be kept as a file.
- **Money stays in cents, and code does the sums.** `read-receipt.ts` turns each amount into integer cents from its two-decimal form, never through float math, and nothing past that file sees dollars. Clairic is never asked to add anything up (Cloudflare's notes on this preview: let code do the math). Code checks that the items add up to the subtotal and that the subtotal, tax and tip, less the discount, make the total, each to the cent; when one doesn't, the review names the number to check and no split is offered.
- **Every value is a guess until kept.** Each value comes with Clairic's confidence and its chance of being missing. A value more likely missing than not is left blank, and every value read shows dashed, "Tally's guess · N% sure", in the one Maybe pattern (§8.6), until a person keeps it; "Looks right" keeps them all (the original's Accept all). A value below the confidence threshold asks to be checked. The threshold is one config value set from the spike, like Jev's (§7).
- **Never the bank's date or amount.** A receipt never changes a bank transaction's date or amount (decision 66). A cash entry made from a receipt takes the receipt's date and total, since it has no bank behind it.
- **Couldn't read it.** When Clairic fails, is switched off, has used the day's reads or finds nothing, the receipt keeps its file and opens the same form empty ("Couldn't read this receipt. Type what it says, or try a clearer photo."), so a person is never stuck. Clairic is a preview that Cloudflare may stop offering; without it, receipts still attach, still match by amount and date, and take what's typed.
- **The switch.** "Read receipts" in Settings' AI suggestions (§8.6): off, nothing is sent to Clairic, and receipts are kept and typed by hand. Items' category guesses also follow Guess categories. What AI did counts the receipts read that a person kept.
- **A daily cap.** At most 100 Clairic reads a household day in production, counted like Jev's calls (`receipt_reads_<date>`, §5); past it, the form opens empty and says why.
- **Kept files.** A kept receipt's photo or PDF stays with it, in R2 with its row in `documents`, and a photo's location and camera data (EXIF) are removed before it's stored, all but its orientation, so it still shows the right way up. The edit panel shows it small and links to the full file. Several receipts can belong to one transaction (Apple bills several purchases as one charge); a receipt belongs to one transaction, bill or plan, and can be moved to another. Moving a receipt from a cash entry to a bank charge first asks to delete the cash entry ("Delete the $23.10 cash entry, so this purchase counts once?"), with the cash delete's 10-second Undo (decision 84); Keep it leaves the receipt where it was, so the purchase is never counted twice by a move. Remove receipt deletes the receipt and its file and never changes the transaction. Every removal (a person's, the 30-day clean-up's, a delete hold's end) first marks the receipt removed (`removed_at`), which hides it everywhere at once, then deletes its files from R2, then its rows; the nightly run finishes any removal left half-done, since deleting an R2 file twice does no harm, so neither a file without a row nor a row without its file is left behind. A receipt still to review after 30 days (never kept, and never set to wait for its charge) is deleted with its file, and the review says so from a week before (the original's clean-up); a waiting receipt is never deleted on its own (step 1).
- **When the transaction changes.** A receipt on a pending charge moves to the posted charge when the bank posts it, as `ai_log` rows do (§5), and so does any `receipt_not_this_charge` row naming the pending charge, in the same write, so a charge a person said No to is never offered again once it posts. If the bank removes a charge, its receipt goes back to waiting. Deleting a cash entry or a plan keeps its receipts' ids in its delete hold (`cash_delete_holds`, `planned_delete_holds`, §5) and sets them aside; Undo links them to the entry or plan it puts back (a plan comes back under a new id), and when the hold ends the receipts and their files are deleted. Splitting moves nothing: the receipt stays on the transaction.
- **Download your data** adds the receipts as a CSV (date, store, total, tax, tip, items, kind, and what each belongs to) and lists each file by name and date, as it lists `documents` today.
- **Privacy and security.** Files live only in the family's bucket and are served only by the family app, behind Access, with their own type and `X-Content-Type-Options: nosniff`, a PDF as a download, never as HTML or SVG. Each upload is checked by its first bytes, not its name or declared type. Clairic runs on Cloudflare, which already holds Tally's data. Nothing read from a receipt or an email is logged (§10). Clairic answers only with typed values, so nothing written in a receipt or an email can make Tally do anything, and every value waits for a person.
- **Accessibility.** The file input is labelled and 44px; "Reading the receipt…" is announced, then how much was found; each item's fields are labelled with its place ("Item 3, Milk"); a split's amount left to assign is announced as it changes; errors use `role="alert"` (§2, CLAUDE.md's rules).

**Step 1: read a receipt and keep it with its purchase**
- **Where.** "Scan a receipt" on Transactions, beside Add cash, and "Add a receipt" in a transaction's edit panel. Both open a sheet with one file input taking JPEG, PNG or WebP photos (the files Clairic reads), up to four for a long receipt, 4 MB each and 8 MB together (Clairic's limits), or one PDF, whose text `toMarkdown` reads first; on a phone it offers the camera or the photo library, and a screenshot works the same way (issue #8's PayPal, Apple and Amazon receipts). No new script: a Read button posts the form as multipart through HTMX (the original sent on pick, which needs a script). A file of another kind or size is refused, naming what's accepted. An iPhone sends a library photo as JPEG when the page asks for JPEG (UNVERIFIED: the spike checks the family's phones; if HEIC arrives, converting it is its own decision).
- **Reading.** The receipt and its file are saved, to review, as soon as they arrive, so leaving the page or losing the connection loses nothing: it waits on the review screen. The file is written to R2 first, under a key made for this receipt, and then its rows in one D1 batch, so either both are saved or the sheet says "Couldn't save. Check your connection and try again." with the form kept (decision 72); a file whose rows were never written is deleted by the nightly run once it's a day old. An emailed receipt is saved in the same order. Clairic reads it while the sheet waits (a few seconds at most, so there's no queue or polling, unlike the original's background job), and the sheet becomes the review. A receipt that looks like one already kept (the same store, date and total) says so on its review, and a person keeps both or removes the new one (the original's duplicate check).
- **From a transaction's panel,** the receipt belongs to that transaction.
- **From Transactions,** it asks how it was paid. Cash makes a cash entry, by Add cash's rules, from the receipt's date, total and store. Card or bank lists the charges it could be: within 5 days of the receipt's date, for the receipt's total, within $2 of it (a surcharge), or the total plus a tip of up to 30% (a restaurant charge posts with its tip); exact amounts first, then charges on the account whose last four the receipt shows, then the nearest date, and charges that already have a receipt after the rest; a split's parts are never listed, only the purchase. A person picks one, or "Not here yet", and the receipt waits for its charge. A card receipt never becomes a cash entry, because its bank charge would then count twice (the original made one and merged it later).
- **Waiting for its charge.** After each sync, Tally looks for each waiting receipt's charge by the same amounts and order, over a wider window: from 5 days before the receipt's date to 30 days after it, since an online order may be charged only when it ships. It never offers one a person said it isn't (`receipt_not_this_charge`, §5), and asks "Is this the receipt's charge?" on the review screen, with the money questions (§8.6). A person always answers; Tally never links a receipt on its own (the original's rule). A receipt still waiting after 30 days asks, on the review screen, to pick a charge, make it cash, or remove it.
- **What keeping it offers.** On its transaction, each dashed until kept: the store as a name suggestion, "From the receipt", after Plaid's own name and never over a person's (§7); what it was, put together by code from its item names (no model writes it), as the note when the note is empty (the note Fill in details' "what it was" fills, decision 103); and, when every item has the same category, that category (step 2). A row with a receipt shows a small receipt mark, drawn in the catalog first.

**Step 2: split a purchase from its items**
- When a receipt's items pair up (as many names as amounts, adding up to the subtotal to the cent), Tally asks Jev for each item's category in one call for the receipt: one Choice question per item, up to 50 items (above that, it guesses none). This adds "and one per receipt" to the one-Jev-call-per-transaction rule; the call counts against Jev's daily cap and follows Guess categories. A receipt whose items got no guesses (Guess categories was off, the day's cap was used, or the call failed) is asked again by the night's Workflow, after its sorting and within what's left of the cap, for receipts kept in the last 30 days, as a switch turned back on catches up (§8.6); an answer that Workflow already keeps for a receipt that hasn't changed is used rather than asked again (decision 143).
- The review lists the items, each with its category folded like a split part's (decision 131), and groups them into split parts by category, so a 15-item receipt becomes one part per category, not 15 parts (the original's open question 4); each part's note names its items. A person changes any item's name, amount or category, adds or removes an item, and saves through the split form, so every split rule still holds. The split form itself offers Add a receipt, for a purchase someone is splitting by hand (the original's "Have a receipt?" in its split modal).
- Tax, tip and discount are shared over the parts in proportion to each part's items, in cents: each part takes its share rounded down, and the leftover cents go one each to the parts with the largest fractions left over (ties to the larger part, then the first listed), so each category carries what it really cost. A transaction with several receipts is split from all of them together: their items combined, each receipt's tax, tip and discount shared over its own items. When the bank's amount differs from the receipts' totals, the difference is shared the same way only when it looks like a tip or surcharge on a single receipt (within $2 of its total, or up to 30% more); any other difference stays as a part of its own, "Not on a receipt", in the transaction's category, so a missing receipt never moves money into the wrong categories. Either way the parts add up to the bank's amount. Adding a receipt to a transaction whose split came from its receipts, unchanged since, offers to split it again from every receipt; a split a person made or changed by hand is never redone.
- When every item has the same category, that category is offered for the whole transaction instead of a split. A transaction a person already split isn't split again; its review shows the items only. Items that don't pair up or add up show as a list beside the receipt's total, and no split is offered.

**Step 3: forward receipts and bills by email**
- **The household's receipts address.** One per household (decision 5), on the family's own domain, with a random part kept in `household_settings` (`receipts_address`), so only someone who has the address can send to it. Settings shows it as text to select (a Copy button needs a script), with "Make a new address", which asks first and retires the old one (the original's regenerate). Production only. The Email Routing rule and any DNS records it needs are shown to the owner and approved before they're made (§11's rule for DNS).
- **Automatic, like Fetch's eReceipts, without giving Tally the inbox.** A family member adds the address as a forwarding address in Gmail (or iCloud Mail) and makes a filter that forwards the stores' receipt emails to it (Walmart, Target, Costco, Instacart, DoorDash, Uber Eats, Apple, PayPal and the like), so they arrive by themselves; Gmail forwards only new mail, never spam. Settings explains the steps for Gmail, iCloud and Outlook (the original's instructions). Forwarding one email by hand works too. Tally never reads anyone's inbox (§12).
- **Gmail's forwarding check.** Gmail confirms a new forwarding address by mailing it a confirmation (from `forwarding-noreply@google.com`, with a link and a code). That one message is accepted from outside the household, by the same sender proof as below for `google.com`: Tally shows only its numeric code in Settings for 7 days ("Gmail asks to confirm forwarding from you@gmail.com. Its code is 123456."), for a person to type into Gmail's forwarding settings, and never shows or follows a link from it, so a forged message can't put a link in front of the family.
- **Who it takes mail from.** The address's random part is only the first lock; the sender must also be proved. Email Routing refuses mail that fails both SPF and DKIM, but passing either one proves nothing about the envelope sender (a forger can pass DKIM for a domain of its own), so the Worker reads Cloudflare's own authentication result for the message (the result Cloudflare's mail servers add, never one written inside the message) and takes it only when SPF passes for the envelope sender's domain, so that domain's own mail servers sent it, and that envelope sender, with Gmail's forwarding tag removed (`you+caf_=…@gmail.com`), is a household address (`household_members`, not removed, decision 82). Gmail and the like send only as the signed-in account, so a pass there ties the message to that person; the From address alone, which anyone can write, never counts. Anything else is refused (`setReject`) and nothing is stored. Step 3 is built only if the spike shows the Worker can read that result (§13 item 10); if it can't, taking receipts by email waits for a decision of its own on another proof. Which envelope sender an iCloud or Outlook rule's forward arrives with, and whether its SPF passes, is checked in the spike before those are offered. At most 50 messages a household day are taken, so even a proved sender can't fill the bucket or spend the reads; and every receipt still waits for a person. If junk arrives, a new address ends it.
- **What it reads.** The Worker parses the message with `postal-mime` (a new dependency, decision 137, the parser Cloudflare's docs use): the HTML body (or the plain text) goes through `toMarkdown` to text, forwarding wrapper and all, so Clairic reads the original receipt; each PDF attachment through `toMarkdown`, as its own receipt; up to four JPEG, PNG or WebP attachments as one receipt's photos, within the same 4 MB each and 8 MB together (a larger photo is kept with the receipt, unread, for a person to type). A message over Email Routing's 25 MiB is refused before it arrives.
- **Amazon's emails carry no items.** Since 2026-07-08 Amazon's order emails give the order total and a link, not the items (step 5 gets Amazon's items, if its file is easy to get); a forwarded one still gives the date, total and order number to find its charge.
- **What it keeps.** The receipt's text and its PDF or photo attachments, as `documents` files, plus the message's Subject and Date (`email_subject`, `email_date`) and its Message-ID or digest (§5), in the same D1 batch; never the raw message, its other headers, or other attachments. A Message-ID seen before is ignored, and one like a receipt already kept says so (step 1's rule).
- **Then** it waits on the review screen like any receipt: an online order is a card receipt, so it waits for its charge (an order charged when it ships arrives before its charge). A message Clairic couldn't read is tried again in the 10:00 run, up to 20 a night and three tries in all (§4.1, §10), then waits as unread with its file. The demo never receives mail.

**Step 4: bills and invoices to pay**
- A bill or invoice (a utility statement, a medical bill, a contractor's invoice), scanned from Bills ("Scan a bill") or forwarded, is read for its payee, amount due, due date and invoice number, as `kind` `bill`. An emailed one is a bill when Clairic finds a due date and an amount due above $0, whatever it says was paid before, since an amount due is what's still owed ("Paid $60; amount due $40" is a $40 bill). It's a receipt only when the amount due is $0 or missing and it shows a payment (an amount paid or a date paid). Code decides this from those values, and a person can switch it.
- The review offers two paths (#21's third phase): "It comes every month" offers the bill whose name or bank text matches the payee, taking the amount due as the bill's amount from its due date's month on (from this month only when no due date was read), so an invoice for next month never changes this month's bill (a bill's amount history, §8.4), or Add a bill filled in from it; "Just this once" opens Plan an expense filled in from it, in its due date's month. When the payment arrives, bill and plan matching link it as they do today (§6.1).
- A paid invoice is a receipt (step 1). Tally never reads an account or policy number into its own fields, only a card's last four; the kept file itself still shows whatever the paper or email shows, and stays in the family's bucket behind Access.

**Step 5: Amazon's order history**

Each finds its charge as a waiting receipt does (step 1). An order whose shipments the file doesn't total stays one receipt (`order_part` 0), which a person links to one of its charges; its other charges keep no receipt. Then steps 1 and 2 offer the name, "what it was" and the split, as for any receipt.
- Uploading again adds only the orders and shipments not seen before (by order ID and shipment). The file itself isn't kept, only what was read from it.
- Only if the file is easy to get (the owner's condition): the spike requests the family's own export and records the steps and the wait, and reads its columns (Amazon renamed the file and some columns in 2026, by one report, UNVERIFIED). The owner sees that before this step is designed; if getting the file is a chore, step 5 moves to the Later list.

### 8.10 Apple Card by upload (decision 138, #731)

Plaid can't reach Apple Card from a web app (its Apple Card path ran only inside Plaid's iPhone SDK, through Apple's FinanceKit, and Plaid deprecated it on March 12, 2026), so Apple Card comes in by file. In one sentence: someone exports their Apple Card transactions as a CSV from card.apple.com or Wallet, uploads it on Accounts, and Tally adds the ones it doesn't have yet. Plaid stays the source for every other bank (decision 3). The owner picked how it looks from pictures at 1280 and 390 (P141 B, below); the pages it touches still start in the catalog like any UI change (DESIGN.md), with a new file field component added to DESIGN.md and the catalog in the same change. It is one component with receipts' file input (§8.9): whichever ships first adds it, and the other uses it.

- **The account.** The first upload creates the household's one Apple Card account (type `credit`, subtype `apple_card`, `is_liability` 1, no Plaid ids), as the first cash entry creates Cash. Apple Card Family shares one account, and a second, separate Apple Card is on the Later list, so a household has at most one. Its transactions count in budgets, Safe to spend, Trends, bills and every other reader exactly as a bank's do.
- **Where it lives (P141 B).** Accounts shows Apple Card as its own group after the banks, drawn like a bank's: its name; "Updated through Oct 18" (the latest Clearing Date it holds; left out until it holds a row) where a bank says "Synced …"; one row, the card icon, "Apple Card" with "Balance as of Oct 18" under it and the balance owed; and an "Upload a file" button under the row, which opens the upload as a sheet over Accounts (the bottom sheet, a right-hand panel on desktop), as Savings opens on Home. Manage holds Remove Apple Card, with the same confirm step as Disconnect a bank (§8.1): by default its transactions stay, so past months still add up, and the account is marked "Removed" and left out of net worth; "Also delete its transactions" removes them too. While it's removed, Home's nudge is off and Accounts offers Add Apple Card again, and the next upload reopens the same account, so its rows are checked against the kept ones and nothing counts twice. Remove forgets the card's balance (`balance_on` is cleared), so a reopened card stays out of net worth until a balance is typed, in the reopening upload or a later one, and the net-worth chart reads its balances only from that new one on (`counted_from`), so an old balance never carries through the months it was removed. Before the first upload, once a bank is linked, Accounts offers "Add Apple Card", an outlined button beside Link a bank, opening the same sheet. Accounts, the net-worth chart, Home's bank notice and Disconnect read only `plaid_items` today; each gains the Apple Card account.
- **The upload.** The sheet is titled "Apple Card" with the card icon, then "Upload the file Apple exports. Tally adds the ones it doesn't have yet." (muted). Its form has no new script: a file field labelled "Apple Card file (CSV)" with "On card.apple.com or in Wallet: Export Transactions, pick the dates, then CSV." (muted) under it (`hx-encoding="multipart/form-data"` when it goes through HTMX) and an optional money input labelled "Balance in Wallet" (the money input, decision 39), with "Optional. Left blank, Oct 12's balance stays. For a credit, type a minus first." (muted; the day is the last balance's, and while the card has no balance the first two sentences are "Optional." alone), then Cancel and Upload. It works from a computer, with the file downloaded from card.apple.com, and from an iPhone, with the file Wallet saved to Files. A request with no Content-Length, or one over 1,100,000 bytes, is refused before its body is read, and a file over 1 MB is refused after (a year of one card is far smaller); the demo's upload sends no file, and its body is never read. Tally reads the file and throws it away: the file is never stored and its rows are never logged. Anyone in the household can upload, and `updated_by` records who did.
- **Which files.** The first line must be one of Apple's two headers exactly: `Transaction Date,Clearing Date,Description,Merchant,Category,Type,Amount (USD)`, with or without `,Purchased By` at the end (Apple adds that column for some cards). Anything else (OFX, QFX, another bank's CSV) is refused whole: "This isn't an Apple Card CSV. In Wallet or on card.apple.com, choose Export Transactions and pick CSV." Tally reads it with a small CSV reader of its own, adding no dependency: a quoted field may hold commas, since Apple puts the store's full address in Description.
- **Each row.** One row becomes one transaction on the Apple Card account:
  - `date` is the Clearing Date, rewritten from Apple's MM/DD/YYYY to YYYY-MM-DD: the same calendar day in Tally's format, never a time-zone conversion (decision 67). Apple's US export writes dates month first; a file with a date that reads only day first (a first number over 12) has an unreadable row, so it's refused whole. Plaid dates a posted transaction by the day it posted, so a purchase on the 31st that clears on the 2nd counts in the month it would at another bank. The Transaction Date is used only in the row's key.
  - `amount_cents` is Amount (USD) read as text into integer cents, never through a float. Apple writes money out as positive, Tally's own sign, so the sign is kept.
  - `raw_name` is Description and `merchant_name` is Merchant, so Apple's Merchant is the merchant key, as Plaid's `merchant_name` is for a bank (§8.5 Merchant), and is suggested as the store's name the same way (§7). Workers AI isn't asked about these rows, since each has a Merchant. Apple's names are uneven (one coffee chain with and without its store number), so one store can be two merchants, each with its own rule; joining them is on the Later list.
  - Apple's Category is kept in its own column, `apple_category`, and goes to Jev as the hint Plaid's category is (§7), never as the answer; category suggestions group Apple Card rows by merchant key, as they do any row Plaid sent no category for. Purchased By isn't stored.
  - `pending` is 0. A row with no Clearing Date hasn't cleared: it's left out and counted in the result, and a later upload brings it in once it clears.
- **Payments never count.** A row whose Type is Apple's word for a payment is the card being paid (`Payment`, confirmed from the owner's export, whose Payment rows carry a Merchant). It's excluded at upload, as Plaid's LOAN_PAYMENTS category excludes the same payment on the checking side (§8.5), so paying the card off is spending on neither side. A bounced payment is left out the same way: an `Other` row whose Description says REVERSAL and whose money is out (decision 144), so a payment and its reversal together add nothing to the month. A person can undo either, as with Plaid's, and no later upload changes a person's choice. It's stored as the bank's own exclusion (`excluded_source = 'plaid'`, which every reader already takes as the bank's label: a transfer the bank marked, lifted when a person marks the credit as income), so the table needs no rebuild; no Plaid sync ever touches an Apple Card row, and nothing on screen names Plaid for it. Every other Type (`Purchase`, `Interest` and `Other`, seen in the owner's export; a refund's word is still unconfirmed, since that export had no refund, and it counts by its sign whatever it is; and any word Apple adds) counts by its sign, as a bank's transaction does: money out is spending, and money in is a refund or credit that refund linking (§6) works on.
- **Nothing counted twice.** Apple's file has no id per row, and identical rows (same dates, Description, Type and Amount) can be two real charges. So each row's key is its Transaction Date, Clearing Date, Description, Type and Amount, and for each key Tally adds only the file's rows beyond the number it already holds with that key on the Apple Card account, none when it holds as many or more. Uploading the same file twice, or ranges that overlap, adds only what's new. Each saved row keeps its place among its twins (1, 2, …), unique with its key on the account, so two uploads at once can't both add the same row. A row a later file lacks is never deleted, because a later file may cover a different range; a person can exclude it.
- **Only Tally's history.** A row whose Clearing Date is before Tally's history starts is left out and counted in the result. The start is the earliest date among the household's bank transactions from Plaid, a disconnected bank's kept ones included; while a connected bank's 90-day history isn't all in yet (`history_complete_at` unset, or no rows so far), it's the earlier of that date and 90 days before the household's today, so no row is left out before the bank's older history arrives. With no bank connected and no bank history kept, the start is the Apple Card's own earliest row, or 90 days before the household's today while it has none, so a card that exists keeps uploading whatever happens to the banks; only a household with no Apple Card yet and no bank has no history to start from, so Apple Card waits for a bank: Accounts' empty state offers only Link a bank, and the upload, if reached directly, says "Link a bank first. Tally's history starts with your bank's." and saves nothing. Older months would hold only the card's spending, and Trends and the first budget suggestions start from the earliest transaction, so they would read those months low.
- **All or nothing.** If any row can't be read (a date, an amount or a column missing or malformed), nothing is saved and the alert names the row: "Row 14's amount can't be read. Nothing was added." A blank Clearing Date (the row hasn't cleared, above), a blank Merchant and a blank Category are allowed (both are stored as NULL); any other missing or malformed field is unreadable. An amount may have a leading minus and thousands commas, and must fit a whole number of cents that's stored exactly (a safe integer, as a cash entry's is); anything else is unreadable.
- **After an upload.** The toast and announcer say what changed: "Added 34 from Apple Card. 6 were already in Tally.", adding "2 haven't cleared yet." or "12 were from before Jul 21, when Tally's history starts." when some were left out, or "Nothing new. All 40 were already in Tally.", or "Nothing new." for a file with no rows (it still counts as an upload) Then the added rows go through what a sync starts (§8.5, §8.6): merchant rules, then bill matching, then Jev in the background, all of them, as a sync's rows are sorted (Cloudflare Workflows in groups of 25, decision 139).
- **The balance.** "Balance in Wallet" is what's owed, stored positive as any card's balance is. A credit balance, money the card owes the family back, is typed with a minus ("-12.00"; this is the one money input that takes one) and stored as a negative amount owed, so net worth adds it. Filled in, it becomes the account's balance and that household day's `balance_history` row (a second upload the same day replaces it), so net worth counts the card. Left blank, the last one typed stays, and the row under Apple Card says its day ("Balance as of Oct 12"). Until a balance has been typed, the card is left out of net worth and Accounts says so: "Apple Card isn't in net worth yet. Add its balance next time you upload."
- **When it's behind.** Home treats Apple Card as a bank that's behind (§8.5) once 7 household days pass since its last upload: the dashed "as of" tag dates Safe to spend by that upload's day, and the soft brick-tinted line, with the card icon, says "Apple Card hasn't been updated since Oct 12" with Upload where a bank's has Fix, opening Accounts with the upload sheet open. It counts from the last upload, not the last charge, so a quiet month doesn't nag. A bank's 3 days stay as they are.
- **The first week.** An upload isn't one of a new family's five strokes: stroke one is still linking a bank, and the questions never wait for Apple Card rows (the first week's counts read Plaid rows only).
- **Demo.** The demo is public, so it never takes a file. Its Upload adds a made-up sample file built into the demo, as if the Riveras had exported it, with a balance of its own, so the demo's sheet has no file field and no balance field; the nightly reset takes it away. Tests also use made-up rows in Apple's layout, never a family's real export.
- **Download your data** lists the Apple Card account and its transactions as it does any account's, with Apple Card as the bank.
- **How Tally works** gains one line where it says where the numbers come from: "Apple Card comes in when you upload the file Apple exports, because Plaid can't reach it. Paying off the card, or a payment that bounced, is left out on both sides, so it never counts as spending."

## 10. Errors, security, and operations

| Situation | Behavior |
|---|---|
| Bank link needs re-authentication (`ITEM_LOGIN_REQUIRED` etc.) | Set `plaid_items.status = needs_attention` and show Fix connection, which opens Plaid Link in update mode. The update-mode `link_token` is created when the button is clicked, never ahead of time, because it expires after 30 minutes. |
| Sync fails partway | Save transactions and the new `sync_cursor` together, in one D1 batch. A retry resumes from the last saved cursor, so nothing is duplicated or skipped. |
| Plaid webhook | Plaid signs every webhook, and the Worker checks the signature against Plaid's published key before trusting it. The `Plaid-Verification` header is a JWT: reject it unless `alg` is `ES256`, fetch the key for its `kid` from `/webhook_verification_key/get` (cached), and verify with Web Crypto (ECDSA P-256). `SYNC_UPDATES_AVAILABLE` starts that Item's transaction sync; Plaid sends it only after an Item's first `/transactions/sync` call, so linking a bank starts that first sync right away, as a repaired connection does; permanent `ITEM` errors, pending expiration or disconnect, and revoked user permission mark it as needing attention. The webhook path is the only path excluded from Cloudflare Access, via an Access **Bypass** policy scoped to `/webhooks/plaid`. |
| Jev unavailable or slow | Leave the transaction uncategorized; the nightly job retries it (in production the next of its Jev runs). AI calls never block a page. |
| Workers AI unavailable | No suggestion; retried the next night (suggestions are made in the night's Workflow, after its sorting, within its 100 and until 13 minutes after their step began). |
| Clairic unavailable, slow, switched off, or the day's reads used (Phase 6) | The receipt keeps its file and opens the same form empty, saying why, so a person can type it (§8.9). A photo isn't retried on its own; a person taps Read again. An emailed receipt is tried again in the next 10:00 run, up to 20 a night and three tries in all, then waits on the review screen as unread. |
| A file Tally can't take (Phase 6) | An upload of anything but a JPEG, PNG or WebP photo or a PDF, a photo over 4 MB, photos over 8 MB together, or more than four photos or one PDF is refused with a field error (`role="alert"`) naming what Tally takes; the type is read from the file's first bytes, never trusted from its name. An emailed photo over those limits isn't refused: it's kept with its receipt, unread, for a person to type (§8.9 step 3). |
| A photo with no receipt in it (Phase 6) | Clairic finds nothing (every value missing): "Tally couldn't find a receipt in this photo." with the empty form. |
| Mail to the receipts address from anyone outside the household (Phase 6) | Rejected, and nothing is stored (§8.9). |
| Invalid input (split doesn't add up, bad amount) | Re-render the form with a field error (`role="alert"`). |
| Logging | Never log tokens, secrets, or transaction details, nor anything read from a receipt or an email (from Phase 6, only a count and an error code). |
| Plaid access tokens | Encrypted with AES-GCM (Web Crypto) using `TOKEN_ENCRYPTION_KEY` before they're stored. |
| Backups | D1 Time Travel restores to a point in time. The retention window gets confirmed in Phase 0 and recorded in the README. |
| Security headers | `X-Frame-Options: DENY`, a strict CSP (no inline scripts; Plaid's CDN allow-listed, and Plaid Link's inline styles allowed, on the Accounts page and on Home in the family app, decisions 63 and 124), and `SameSite=Lax` on any cookie. |
| Form posts from other sites | Rejected with 403 unless the browser shows the post came from this site (`Sec-Fetch-Site: same-origin` or a matching `Origin`), using Hono's built-in `csrf` middleware. |
| Web Push (decision 148) | A device's push subscription is kept per person (`push_subscriptions`), is left out of Download everything, and is deleted when its person is removed. Pushes are signed with the server's VAPID key pair (two secrets, production only). A push service's 404 or 410 deletes that device; no answer, a 429 or a 5xx is retried each minute while no device has answered with a success, until the email goes; any other 4xx is refused for that push and not retried every minute. Logs hold counts and status codes only, never an endpoint or a key. |
